# Карточки CRM через модерацию — проект

Дата: 14.09.26 · основание: решение руководителя по открытому вопросу 4 разбора
`.claude/docs/topnlab/plugin-integration-assessment.md` («почему лиды с сайта не уходят в CRM»).

## 1. Решение

Ни заявка, ни объект не пишутся в CRM Topnlab автоматически. Путь один — и для
лида с сайта, и для карточки, заведённой в Telegram:

```
лид назначен сотруднику
  → сотрудник связался с клиентом
  → дозаполнил карточку
  → машинная проверка полей
       ├─ замечания → доработка сотрудником
       └─ чисто     → на модерацию директору
                         ├─ вернуть на доработку (с комментарием)
                         ├─ поправить поля самому
                         └─ одобрить → выгрузка в CRM
```

Права сотрудника на создание заявок, объектов и на модерацию **наследуются из
CRM** — по должности и статусу его учётки в Topnlab.

Почему так: заявка с формы сайта бывает спамом, а в CRM мы сознательно не
удаляем (ТЗ плагина, §5.6). Мусорная карточка там остаётся навсегда. Ручная
модерация дешевле, чем чистка CRM.

## 2. Что уже есть и на что встаём

| Есть | Где | Как используем |
|---|---|---|
| Лид с сайта → карточка в Telegram, назначение, стадии | `Lead::Intake`, `LeadAnnouncer`, `LeadAssignment`, `/stage` | вход конвейера; «контакт с клиентом» = стадия не `new` или `first_contact_at` |
| Кнопка «Спам» | `Callbacks::SpamCallback` → лид `closed_lost` | закрытый лид не проходит машинную проверку |
| Пошаговые мастера в личке | `Wizard::Engine` + `Flow` | заполнение, правка поля, возврат, одобрение, ручная выгрузка |
| Создание заявки в CRM | `Topnlab::Client#import_client` — **не вызывается нигде** | единственный вызов — выгрузка одобренной карточки |
| Назначение ответственного в CRM | `Topnlab::Client#transfer_client` | ответственный = текущий ответственный по лиду |
| Должность и статус сотрудника из CRM | `users.crm_role_id / crm_role_name / crm_status`, ночной `TopnlabStaffSyncJob` | источник прав |
| Связь «Telegram ↔ CRM» | `telegram_users.topnlab_user_id` (через `/whoami`) и `users.telegram_user_id` | обе обязаны указывать на одну учётку |

Проверено 14.09.26: `Inquiry#sync_to_crm!` — пустая заглушка (вызов AmoCRM
закомментирован). Обходного пути заявки с сайта в CRM нет; план закрепляет это
спекой.

## 3. Права: что значит «наследовать из CRM»

Публичный API Topnlab (`getUsers`) отдаёт по сотруднику только **должность**
(`role` / `role_name`), **статус** (активен / уволен / приглашён / заблокирован)
и отдел. Списка прав роли в нём нет — он виден только через внутренний API под
токеном пользователя, а шлюз к нему ещё не построен.

Поэтому в этой версии:

- **что наследуется из CRM автоматически** — назначение должности и статус.
  Директор сменил сотруднику должность или уволил в Topnlab → после ночной
  синхронизации права в боте меняются сами;
- **мост «должность → возможности»** — таблица `config/crm_permissions.yml`,
  ключ — id должности в CRM. Должность вне таблицы прав не имеет;
- **роль в боте (`telegram_users.role`) прав не даёт.** Её ставят вручную
  `/promote`, и сейчас она расходится с CRM (см. §6).

Когда появится шлюз (`crm_whoami` с модулями роли), таблица заменяется ответом
CRM. Интерфейс `CrmCards::Permissions::Result#can?` остаётся прежним — вызывающий
код не меняется.

Возможности: `create_lead`, `create_object`, `moderate`.

Отказ по умолчанию и с объяснением: бот неактивен, нет `topnlab_user_id`, учётки
нет в справочнике, две разные учётки на одном телеграме, учётка в CRM не
`active`, должность вне таблицы.

## 4. Карточка

`CrmCard` — одна модель на оба вида, soft-delete.

| Статус | Смысл | Кто правит поля |
|---|---|---|
| `draft` | черновик | ответственный (или модератор) |
| `needs_rework` | возвращена с комментарием | ответственный (или модератор) |
| `pending_review` | на модерации | только модератор |
| `approved` | одобрена | никто; объект вносит в CRM ответственный |
| `exporting` | выгрузка идёт | никто |
| `exported` | в CRM, `crm_id` известен | никто |
| `export_failed` | выгрузка не удалась | никто; модератор повторяет |

Каждый переход пишется в `crm_card_transitions` (кто, откуда, куда, комментарий).
Все переходы — только через `CrmCards::Workflow`.

**Поля — ровно то, что можно выгрузить.**
Заявка повторяет параметры `import_client`: имя, телефон, продажа/аренда, тип
объекта, итог разговора (20–500 символов), id объекта в CRM (необязательно).
Объект — минимум формы «Создать объект Продавца» (ТЗ плагина, §6): собственник,
телефон, сделка, тип, адрес, цена, площади, комнаты, этажи, договор.

**Одна карточка заявки на лид.** Карточку заявки ведёт **текущий ответственный
по лиду** (`CrmCard#responsible`), а не тот, кто её начал: лид переназначили —
править и отправлять может только новый ответственный (или модератор), и
ответственным в CRM станет он, даже если переназначили уже после отправки на
модерацию. У объекта ответственный — автор.

## 5. Машинная проверка

Проверяет то, что машина может проверить; модератор смотрит на то, что не может
(правдоподобие, дубли).

Заявка:
- обязательные поля заполнены, значения валидны (телефон — 11 цифр с 7);
- итог разговора не короче 20 символов;
- лид назначен, не закрыт, не тестовый;
- **с клиентом был контакт**: стадия не `new` или стоит `first_contact_at` — это и
  есть спам-фильтр;
- у клиента ещё нет заявки в CRM (`lead_ref.crm_id` пуст).

Объект:
- обязательные поля; условные: для квартиры — комнаты, для участка — площадь
  участка вместо общей, для агентского договора и соглашения на рекламу — номер;
- общая площадь ≥ жилая + кухня; этаж ≤ этажности.

Не проверяется в этой версии (нужен шлюз): обязательность полей под ролью
(`formconstructor`), дубли по телефону/адресу/кадастру, наличие копии договора.

## 6. Выгрузка

**Заявка — через API.** `approved → exporting` захватывается атомарно
(`update_all ... where status = 'approved'`), иначе двойной запуск джоба заведёт
две заявки. `import_client` → `transfer_client` на email текущего ответственного. Сбой назначения
ответственного выгрузку не отменяет — возвращается предупреждением. Автоповтора
нет: Topnlab не идемпотентна, повтор после таймаута создаёт дубль. Повтор —
кнопкой модератора, с напоминанием сначала найти клиента в CRM по телефону.
Кнопка появляется и у заявки, которая дольше 15 минут висит в «выгружается»
(упал процесс) или в «одобрена» (джоб не встал в очередь) — иначе такую
карточку не сдвинуть ничем; обе попадают в `/cards` в «Сбои выгрузки».
После выгрузки `crm_id` проставляется в `Inquiry` — с этого момента
`LeadAssignment#push_to_crm` и `SpamCallback` работают с лидом как с пришедшим из CRM.

**Объект — вручную.** Создать объект через публичный API нельзя (разбор, §2.2).
Одобренный объект автор получает в личку «паспортом» для ввода в CRM, вносит
его и отмечает номер карточки; до этого объект виден ответственному в `/cards`.
Автоматическая выгрузка объектов — после шлюза.

## 7. Интерфейс — только Telegram

Сотрудники живут в Telegram, веб-интерфейса не строим (`reglament/DESIGN.md`).

- Под карточкой лида — кнопка «📋 Карточка CRM» или статус карточки.
- Назначенному на лид в личку — та же кнопка с напоминанием.
- Карточка с телефоном клиента — **только в личке**, никогда в группе.
- `/cards` — мои черновики и возвраты; модератору ещё очередь и сбои выгрузки.
- «☰ Что сделать?» → «🏠 Новый объект в CRM» — у кого есть `create_object`.

Учётка «Генеральный директор» (89884) в CRM активна, но **к Telegram не
привязана**. Пока это так, модерировать некому, и `submit!` честно отказывает

своей учётки «Генеральный директор», затем `bin/rails crm_cards:permissions`.

## 9. Вне рамок

- Шлюз к внутреннему API и всё, что на нём: права из `crm_whoami`, дубли,
  обязательность полей под ролью, автоматическое создание объектов.
- Вложения (копия договора, фото) — вносятся в CRM вручную.
- Правка или удаление в CRM уже выгруженной карточки.
- Веб-админка карточек.

## 10. Открыто для руководителя

1. **Таблица должностей.** По умолчанию: Ген. директор — всё; Агент — заявки и
   объекты; Стажёр — только заявки; Конструктор, Аудитор, Юрист — ничего.
   Подтвердить или поправить `config/crm_permissions.yml`.
2. **Кто модерирует в отсутствие директора.** Сейчас — любой с `moderate`. Если
   нужен заместитель — дать его должности `moderate` в таблице.
