# Правила ведения документации

Дата введения: 12.10.26. Обязательны для людей и AI-агентов.
Нарушение этих правил в PR — повод для request changes.

## 1. Иерархия источников правды

| Уровень | Что | Где живёт |
|---|---|---|
| 1 | **Источник правды о проекте** | `AGENTS.md` + `.claude/memory/` (`activeContext.md`, `systemPatterns.md`, `techContext.md`, `progress.md`, `strategicVector.md`) |
| 2 | **Манифесты подсистем** | `services/*/SERVICE.md` (проверяются `bin/services-check` в CI) |
| 3 | **Эксплуатационные процедуры** | `docs/runbooks/*.md` |
| 4 | **Бизнес-регламенты** | `.claude/docs/reglament/` |
| 5 | **Планы и мастер-документы** | `.claude/plans/_shared/` — меняются **только через PR** |
| 6 | **Для пользователей GitHub** | `README.md` — краткая витрина, детали отдаёт ссылками в уровни 1–3 |

Корневые `*.md` (`STATUS.md`, `SUMMARY.md`, `DEPLOYMENT*.md`, `ROADMAP.md` и др.) —
**исторический шум**. Не обновлять, не ссылаться на них, не считать актуальными.
Новые документы в корень не класть.

## 2. Принцип «код меняется — документация меняется»

- Изменил поведение, которое описано в `AGENTS.md` / memory-bank / SERVICE.md /
  runbook — обнови соответствующий документ **в том же PR**. Документация,
  расходящаяся с кодом, хуже отсутствующей.
- Добавил службу в `services/` — создай `SERVICE.md` (иначе упадёт
  `bin/services-check`) и заполни по шаблону соседних служб.
- Добавил периодическую задачу — она идёт в `config/sidekiq_cron.yml`, а её
  назначение отражается в `.claude/memory/techContext.md`, если это боевой контур.
- Добавил ENV-переменную — дополни `.env.example` с комментарием; боевые группы
  переменных фиксируются в `.claude/memory/techContext.md`.
- После структурных изменений кодовой базы регенерируй индексы:
  `bin/rb bundle exec rake repo:map` (обновляет `.claude/repo-index.md` и
  `.claude/repo-map.md`).

## 3. Куда писать новый документ

| Тип документа | Куда |
|---|---|
| Правило/конвенция кода | `.claude/memory/systemPatterns.md` |
| Стек, ENV, команды, процедуры | `.claude/memory/techContext.md` или `docs/runbooks/` |
| Текущее состояние/фокус работы | `.claude/memory/activeContext.md` |
| Что в проде, tech-debt | `.claude/memory/progress.md` |
| Манифест службы | `services/<name>/SERVICE.md` |
| Витрина проекта | `README.md` |

Не плодить новые корневые `*.md`. Отчёты о сессиях, «final report», «summary» —
в `.claude/` или не писать вовсе.

## 4. Стиль

- **Язык: русский.** Исключение — имена сущностей, команды, пути, ключи ENV.
- **Даты — европейский `dd.MM.yy`** (общее правило проекта, действует и в документации).
- **Проверяемость.** Каждое утверждение должно быть подкреплено файлом/командой:
  пишем `config/sidekiq_cron.yml`, а не «где-то в конфигах». Версии берём из
  `Gemfile`/`Gemfile.lock`/`Dockerfile`, а не из головы.
- **Краткость.** Документ отвечает на вопрос «что нужно знать, чтобы не сломать».
  Историю решений — в commit message и PR, не в эксплуатационные документы.
- **Без мёртвых бейджей и выдуманных метрик** (покрытие, «build passing» без CI-ссылки).
- **Без секретов.** Только имена ENV-переменных, никогда значения. Примеры —
  в `*.example` файлах.
- Таблицы — для справочных данных; вложенность заголовков — не глубже третьего уровня.

## 5. Жизненный цикл

- Документ без владельца и даты обновления устаревает молча — указывай дату
  последней проверки в начале runbook'ов и долгоживущих инструкций.
- Устаревший документ **удаляется или переписывается**, а не дополняется
  оговоркой «это неактуально». История сохраняется в git.
- Незавершённый перенос службы обязан иметь дату `repatriate_by` в `SERVICE.md`.
- Раз в квартал (или при смене релизной линии) — сверка `README.md` и `AGENTS.md`
  с фактическим состоянием: версии в `Gemfile`, список служб в `services/`,
  состав cron-задач в `config/sidekiq_cron.yml`.

## 6. Процесс изменения

1. Правки документации — теми же PR, что и код, либо отдельным PR с префиксом `docs:`.
2. Мастер-документы `.claude/plans/_shared/` — **только через PR**, без исключений.
3. При ревью PR проверять: не устарела ли документация из-за этого diff
   (чек-лист для ревьюера: `AGENTS.md`, memory-bank, SERVICE.md, README, runbook).
4. Спор о том, где должен жить документ, решается таблицей из раздела 3.
