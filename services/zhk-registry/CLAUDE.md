# CLAUDE.md — zhk-registry

Python-служба внутри Rails-репозитория. Корневой `CLAUDE.md` и skill
`victory-rails-conventions` сюда **не применяются** — из трёх жёстких
правил репозитория едет только одно: даты `dd.MM.yy`.

## Чем отличается от Rails-части

| | Здесь |
|---|---|
| Язык, зависимости | Python + pydantic + `requests`, пины в `requirements.txt`. Не bundler |
| Тесты | stdlib `unittest`, не pytest и не rspec |
| Данные | нет своей БД и нет доступа к Rails-БД. Всё состояние — на стороне victory62 |

## Запуск тестов

```bash
cd services/zhk-registry && python3 -m unittest discover -v
```

Только **из каталога службы** — импорты плоские (`from observation import
...`), `unittest discover` кладёт текущий каталог в `sys.path` сам. Из
корня репозитория не сработает.

Тестам нужны `pydantic` и `requests` — если их нет в системном Python,
поставить в одноразовый venv:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m unittest discover -v
```

Сеть и БД тестам не нужны вообще: `client.py` тестируется на подменённом
`requests.post`, реального похода к серверу не происходит.

## Контракт наблюдения — не своя собственность

`observation.py` обязан парсить
`../../spec/fixtures/zhk/observation_example.json` — файл общий с
Rails-тестами (`spec/requests/webhooks/zhk_ingest_controller_spec.rb`).
Меняя контракт наблюдения:

1. правь образец в `spec/fixtures/zhk/`;
2. правь `Observation` здесь;
3. проверяй Rails-сторону (`Zhk::Ingest`, контроллер) — рассинхрон полей
   не поймает ни один из двух прогонов тестов по отдельности, только оба
   сразу.

Не заводи здесь свою копию образца «для скорости» — единственная причина,
по которой тест вообще замечает разъехавшийся контракт, это то, что обе
стороны читают один и тот же файл.

## Что нельзя делать в этой службе

- **Импортировать Rails-код.** Никаких `require 'active_record'`,
  никакого чтения моделей — связь с victory62 только через HTTP-вебхук
  `POST /webhooks/zhk_ingest`.
- **Импортировать другие каталоги `services/`.** `services/zhk-registry`
  не тянет `urgent-news-collector`, `audit-engine` и т.п. — общих модулей
  между питоновскими службами репозитория нет и не планируется без
  отдельного решения.
- **Писать в БД напрямую.** Ни к прод-БД victory, ни к какой-либо своей —
  вебхук единственный канал записи.
- **Резать батч ближе к серверному лимиту, чем 50.** Сервер отвергает
  батч длиннее `MAX_BATCH` (50) целиком, 422 — клиент режет заранее в
  `IngestClient.send`, полагаться на серверный отказ и ретраить хвостом
  нельзя.
- **Трактовать `status: invalid` как временный сбой.** Это «не примем
  никогда»; ретраить такое наблюдение бессмысленно, в отличие от HTTP 503
  (пустой `ZHK_INGEST_TOKEN` на сервере — конфигурационный сбой, его
  ретраить стоит).
