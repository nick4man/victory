# zhk-registry

Питоновская сторона «Реестра новостроек Рязани». Собирает наблюдения об
объектах в открытых источниках (ЕРЗ, сайты застройщиков, агрегаторы) и
отправляет их на вход Rails-стороны, которая уже сопоставляет наблюдение с
карточкой ЖК, пишет провенанс и раскладывает противоречивые поля в очередь
расхождений для редактора.

Продюсер для эндпоинта
`app/controllers/webhooks/zhk_ingest_controller.rb` из этого же
репозитория.

## Что здесь есть сейчас

Контракт, клиент отправки, два источника (ЕРЗ и сайт застройщика
«Единство») и крон-оркестратор, который сводит их вместе:

| Файл | Что |
|---|---|
| `observation.py` | `Observation` (pydantic) — форма одного наблюдения и её валидация. `to_payload()` отдаёт JSON ровно в форме, которую ждёт вебхук |
| `client.py` | `IngestClient` — шлёт наблюдения на `POST /webhooks/zhk_ingest`, режет батч по 50 сам, до отказа сервера не доводит |
| `sources/base.py` | Протокол `Source` (`discover`/`enrich`) и `polite_get` — вежливый GET с паузой и представленным User-Agent, общие для всех адаптеров |
| `sources/erz.py` | `ErzSource` — обнаружение ЖК Рязани и разбор карточки на erzrf.ru. Вес источника — 2 (агрегатор, вторичный) |
| `sources/edinstvo.py` | `EdinstvoSource` — карточки ЖК на сайте застройщика «Единство». Вес — 3 (первичный источник по своим объектам) |
| `run.py` | Точка входа крона: обходит источники по очереди, изолирует падение каждого, ретраит транзиентные сбои отправки, шлёт сводку прогона. Ставится в крон `crontab.example` |

### ЕРЗ.РФ — что реально можно снять без JavaScript

erzrf.ru — Angular SPA, и его `serverApp-state` (для гидратации) на живых
страницах всегда пустой JSON — сервер не рендерит в него данные
предметных виджетов. Отсюда разделение фактов по двум страницам:

- страница списка региона отдаёт статикой название, ссылку, этажность и
  срок сдачи по ЖК — их собирает `ErzSource.discover()`;
- карточка ЖК отдаёт статикой только «паспортную» таблицу (регион,
  населённый пункт, застройщик, улица) — их собирает `ErzSource.enrich()`
  через `parse_card()`.

`enrich()` переносит найденное в `discover()` (этажность, срок сдачи) в
итоговое наблюдение как есть, без нормализации — «III кв. 2026»,
«IV кв. 2026» и «Сдан» остаются в исходном виде: сравнивать такие записи
между собой — работа Rails-стороны.

## Контракт — общий с Rails, а не свой

`Observation` обязана парсить
`spec/fixtures/zhk/observation_example.json` — этот файл лежит в
Rails-дереве и используется и `spec/requests/webhooks/zhk_ingest_controller_spec.rb`,
и тестами этой службы. Если образец правят на одной стороне, тесты обеих
сторон обязаны упасть одновременно — иначе контракт разъезжается молча.

Поля наблюдения:

```json
{
  "source": "erz",
  "url": "https://erzrf.ru/novostroyki/zhk-skobelev-564336001",
  "external_id": "erz:564336001",
  "fetched_at": "2026-09-07T05:00:00Z",
  "name": "Скобелев",
  "city": "Рязань",
  "fields": { "developer": "Единство", "built_to": 2022 },
  "price": { "kind": "from", "price_per_sqm": 65000, "rooms": null }
}
```

`source` + `external_id` вместе — внешний идентификатор наблюдения,
которым Rails-сторона ловит дубликаты и обновления.

## Батч режется здесь, не на сервере

Вебхук отвергает батч длиннее 50 наблюдений целиком (422) — это защита
сервера, а не то, на что клиенту стоит полагаться. `IngestClient.send`
режет список на куски по 50 сам и шлёт их последовательными запросами;
до отказа `422 batch_too_large` доводить нельзя.

## Смысл кодов ответа для клиента

Построчный `status` в `results` и HTTP-код запроса значат разное, и
путать их нельзя:

| Что | Значит |
|---|---|
| `status: invalid` у наблюдения | не примем никогда, ретраить бессмысленно |
| `status: duplicate` | уже есть, всё хорошо, не ошибка |
| HTTP 4xx на весь запрос | вина запроса (плохой токен, батч не по контракту) |
| HTTP 503 | секрет `ZHK_INGEST_TOKEN` не выставлен на сервере — это поломка конфигурации Rails-стороны, а не отказ навсегда; такой запрос стоит повторить позже |

## Оркестратор и сводка прогона

`run.py` обходит источники ПО ОЧЕРЕДИ и изолирует падение каждого:
упавший ЕРЗ (недоступен `discover()`, отправка не восстановилась даже
после ретраев) не мешает обойти «Единство» следом. Транзиентные сбои
(HTTP 5xx, обрыв сети) ретраятся на трёх уровнях — `discover()`,
отправка батча, POST сводки — общим ретрай-циклом `call_with_retry`;
`invalid`-ответ и HTTP 4xx не ретраятся никогда, см. докстринги
`is_transient`/`call_with_retry`. `count` источника — это число
наблюдений, которые сервер РЕАЛЬНО применил (`status != invalid`), а не
просто сколько было отправлено: батч, отвергнутый целиком, не должен
выглядеть в сводке как полный успех.

После обхода всех источников (успешных и упавших) `run.py` шлёт
`POST /webhooks/zhk_ingest/summary` с `{"counts": {"erz": N,
"edinstvo": M}}`. На Rails-стороне `Zhk::RunSummary` пишет каждое
число в журнал `ZhkIngestRun` (не в `zhk_observations` — тот считает
только новый/изменившийся контент и почти всегда околонулевой на
статичном каталоге, см. докстринг миграции
`db/migrate/*_create_zhk_ingest_runs.rb`) и применяет ДВА правила:

- **фронтовое** — count этого прогона кратно (порог 30%) меньше
  ПРЕДЫДУЩЕГО: ловит МОМЕНТ поломки;
- **уровневое** (круг правок 2) — count этого прогона строго ноль, и у
  источника уже есть история: срабатывает КАЖДЫЙ прогон, пока источник
  не отклеится от нуля, а не один раз на переходе. Без него источник,
  молчащий вторую неделю подряд (когда прошлый прогон уже был нулём),
  сравнивался бы сам с собой и «выглядел стабильным», а источник,
  мёртвый с рождения, не поймался бы вовсе — момента перехода «жив →
  мёртв» у него никогда не было.

Оба правила требуют хотя бы один предыдущий прогон — новый источник не
считается молчащим (сравнивать не с чем). Подробности — в докстринге
`app/services/zhk/run_summary.rb`.

Ответ сервера несёт `delivered: true/false` — принят запрос ещё не
значит, что сводка дошла до сотрудников в Telegram (`TELEGRAM_STAFF_CHAT_ID`
может быть не настроен, сам Telegram — недоступен). `run.py` завершается
ненулевым кодом, если `delivered` не `true`.

Расписание — `crontab.example` (раз в неделю, `flock -n` от наложения
прогонов, `MAILTO` + `|| echo` — иначе ненулевой код возврата никуда не
долетит: cron рассылает почту по СВОЕМУ stdout/stderr, а не по коду
возврата задачи, и версия без этого была бы декорацией — код правильный,
канал не подключён).

## Первый запуск

Сухой прогон 08.09.26 прошёл по шагам ниже на живом локальном стеке
(worktree `victory-registry`, RSpec 242/242, python-тесты 61/61 зелёные).
Команды здесь — то, что реально сработало, а не то, что было в
изначальном плане: план трижды ошибался с URL/путями источников, а
предложенная в задаче curl-команда для вебхука отправляла не тот payload
(см. пункт 2 ниже) — обе ошибки исправлены здесь, без них шаги ниже не
воспроизводятся.

### 1. Окружение службы

```bash
cd services/zhk-registry
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env
# заполнить VICTORY_BASE_URL, ZHK_INGEST_TOKEN (то же значение, что
# ZHK_INGEST_TOKEN в .env Rails-стороны), CRAWLER_CONTACT
```

Без `VICTORY_BASE_URL`/`ZHK_INGEST_TOKEN` в `.env` боевой запуск (`DRY_RUN`
не установлен) падает сразу на первой строке `main()` с `KeyError` — это
намеренно: тихо слать наблюдения в никуда хуже, чем упасть явно.

### 2. Проверка селекторов на живых источниках (DRY_RUN)

Ни один из адаптеров не проверить по фикстурам «а реально ли сайт всё
ещё так выглядит» — для этого `DRY_RUN`:

```bash
DRY_RUN=1 .venv/bin/python3 run.py
```

В этом режиме `VICTORY_BASE_URL`/`ZHK_INGEST_TOKEN` необязательны
(клиент создаётся, но ни разу не используется) — режим только для
проверки `discover()`/`enrich()`, вебхук не участвует вовсе, ни батчи,
ни сводка никуда не уходят.

**Это не быстро.** `polite_get` держит паузу 12 секунд перед каждым
запросом (`sources/base.py::DELAY_SECONDS`) — на прогоне 08.09.26 ЕРЗ (10
карточек) занял ~3 минуты, «Единство» (46 карточек) — ~10.5 минут,
итого около 14 минут на оба источника. Не значит, что скрипт завис —
значит, что он вежливый.

Ожидаемый вывод — строки вида:

```
INFO DRY_RUN erz:23500236001 | Среда (Рязань) — {'developer': 'ООО СЗ Среда', 'floors': '9', 'commissioning': 'от III кв. 2026'}
...
INFO erz: нашли (DRY_RUN) 10
INFO DRY_RUN edinstvo:128 | Пожарский (Рязань) — {'developer': 'Единство'}
...
INFO edinstvo: нашли (DRY_RUN) 44
INFO DRY_RUN: сводка прогона не отправляется, итог по источникам: {'erz': 10, 'edinstvo': 44}
```

Два наблюдения по факту прогона 08.09.26, которые стоит держать в
голове, читая свой собственный вывод:

- **`edinstvo` находит карточки ДОМОВ, а не ЖК** — 44 в счётчике
  против ~12 засеянных комплексов не ошибка: домашняя страница
  `edinstvo62.ru` отдаёт по `/building/<id>` на каждый корпус/подъезд, а
  несколько корпусов одного ЖК сводятся в одну карточку справочника уже
  на Rails-стороне (`Zhk::Matcher` по имени/адресу). Резкое падение этого
  числа в РАЗЫ (а не на единицы) — вот что стоит считать сигналом отказа
  селектора, не сам факт «не 12».
- **Единичные пропуски карточек — норма, а не повод паниковать.** В
  прогоне 08.09.26 две карточки «Единства» (`/building/10`, `/building/57`)
  словили `ConnectTimeoutError` и были молча пропущены — это ожидаемое
  поведение адаптера (см. докстринг `run.py`, пункт 1: сетевой обрыв
  внутри `enrich()` не ретраится, просто теряет одну карточку). Один-два
  потерянных URL из полусотни не значит, что источник замолчал.

Пусто по источнику целиком (0 карточек, не 1-2 потерянных) — вот это уже
селекторы разошлись с текущей вёрсткой, чинить `sources/erz.py` /
`sources/edinstvo.py` до боевого запуска (см. секцию ниже про молчащий
источник).

### 3. Проверка вебхука на локальном Rails-стеке

Из корня Rails-репозитория (не отсюда):

```bash
bin/rb --web up                     # если порт 3001 занят соседней сессией — RB_WEB_PORT=<свой>
# в .env Rails-стороны должен быть ZHK_INGEST_TOKEN (иначе 503, см. ниже) —
# добавить строку и один раз пересоздать web-контейнер, чтобы ENV подхватился
bin/rb --web 'bin/rails runner "puts ENV[\"ZHK_INGEST_TOKEN\"].inspect"'
```

**Важно про фикстуру.** `spec/fixtures/zhk/observation_example.json` —
это форма ОДНОГО наблюдения, а не тела запроса целиком. Отправить файл
как есть — гарантированный `422 invalid_payload` («observations must be
an array»): вебхук ждёт `{"observations": [...]}`. Рабочая форма:

```bash
python3 -c "
import json
obs = json.load(open('spec/fixtures/zhk/observation_example.json'))
json.dump({'observations': [obs]}, open('/tmp/zhk_batch.json', 'w'))
"
curl -s -X POST http://127.0.0.1:3001/webhooks/zhk_ingest \
  -H 'Authorization: Bearer <ZHK_INGEST_TOKEN>' -H 'Content-Type: application/json' \
  -d @/tmp/zhk_batch.json
```

Ожидаемо: `{"results":[{"external_id":"erz:564336001","status":"created",...}]}`.
Повторная отправка того же файла — `"status":"duplicate"`, без изменений
в базе (проверено 08.09.26).

Проверка режимов отказа авторизации (прогонялась вручную, все три
подтвердились):

| Что послать | Ответ |
|---|---|
| `ZHK_INGEST_TOKEN` пуст на сервере | `503` — поломка конфигурации, не отказ навсегда |
| `Authorization: Bearer <неверный токен>` | `401` |
| `Authorization: <токен без префикса Bearer>` | `401` — голое значение не аутентифицирует, даже если оно верное |
| батч из 51 наблюдения | `422 batch_too_large` — целиком, ничего не пишется |

Погасить стек: `bin/rb --web down`. На свежем volume (`bin/rb --nuke` до
этого) сначала нужен `bin/rails db:migrate` — Rails-сторона не
поднимается сама по себе на пустой БД.

⚠️ На ПОЛНОСТЬЮ пустом volume (найдено 08.09.26, к самой ЖК-фиче не
относится) `db:migrate`/`db:schema:load` может упасть на `ERROR: schema
"tiger" already exists`: кастомный образ `viktory-postgres-pgvector`
создаёт `tiger`/`tiger_data`/`topology` при инициализации, а
`db/structure.sql` создаёт их же без `IF NOT EXISTS`. Обходной путь (не
чинит первопричину, только разово расчищает volume):
`docker exec <db-контейнер> psql -U postgres -d viktory_realty_development
-c 'DROP SCHEMA tiger CASCADE; DROP SCHEMA tiger_data CASCADE; DROP SCHEMA
topology CASCADE;'`, затем `db:migrate` заново. Отдельно от этого —
`db/migrate/20260527000900_add_nextcloud_to_client_documents.rb` по
таймстампу идёт РАНЬШЕ `db/migrate/20260527020000_create_client_documents.rb`
и на честном `db:migrate` с нуля падает, потому что нужной таблицы ещё
нет: если упёрлись в это, `bin/rails db:migrate:up
VERSION=20260527020000`, затем обычный `db:migrate` подхватит остальное
по порядку.

### 4. Крон

`crontab.example` — раз в неделю, `flock -n` от наложения прогонов,
`MAILTO` для алертов. Ставится на хосте прода (`crontab -e`
пользователя, не `/etc/crontab`), путь внутри — main-чекаут
(`/home/q/victory/services/zhk-registry`), не сессионный worktree
разработки. Подробности — комментарии в самом файле.

### 5. Логи и куда смотреть

- **stdout/stderr прогона** — `/var/log/zhk-registry.log` (см.
  `crontab.example`); ненулевой код возврата (сводка не доставлена)
  долетает до `MAILTO` через `|| echo` в самой крон-строке.
- **Rails-сторона** — таблица `ZhkIngestRun` (журнал `count` по
  источнику за каждый прогон, на ней стоит детектор молчащего
  источника, `app/services/zhk/run_summary.rb`) и Telegram-канал
  `TELEGRAM_STAFF_CHAT_ID` (туда уходит текст сводки, если настроен).
- **Экран расхождений** — `/admin/zhk_discrepancies?token=$ADMIN_TOKEN`:
  если два источника прислали разные значения одного поля одного ЖК,
  оба значения со ссылками на источник и датой наблюдения (`dd.MM.yy`)
  видны здесь, поле в карточке ЖК остаётся пустым, пока расхождение не
  разрешит редактор вручную.

### 6. Источник замолчал — что делать

1. Прогнать `DRY_RUN=1 .venv/bin/python3 run.py` и посмотреть на
   конкретный источник: 0 карточек (не 1-2 потерянных) от `discover()`
   или обвал `enrich()` по всем карточкам подряд — вёрстка сайта
   разошлась с селекторами.
2. Обновить фикстуру источника (`tests/fixtures/erz_list.html`,
   `erz_card.html`, `edinstvo_list.html`, `edinstvo_card.html`) свежей
   версией страницы — `curl` с тем же User-Agent, что в `sources/base.py`.
3. Починить селектор в `sources/erz.py`/`sources/edinstvo.py` под новую
   вёрстку.
4. Прогнать тесты: `python3 -m unittest discover -v` — фикстура и
   парсер обязаны сойтись.
5. Повторить DRY_RUN на живом сайте, убедиться что карточки снова
   находятся, и только после этого — боевой прогон.

Если детектор молчащего источника уже сработал в Telegram (текст
`🚨 молчат: <источник>`) — это `Zhk::RunSummary` увидел падение count
кратно (порог 30%) относительно прошлого прогона, ИЛИ источник третий
прогон подряд отдаёт строгий ноль. Оба правила требуют хотя бы одного
предыдущего прогона в истории — на новом источнике тревога не сработает
(сравнивать не с чем), см. докстринг `app/services/zhk/run_summary.rb`.

## Запуск тестов

```bash
cd services/zhk-registry && python3 -m unittest discover -v
```

Без сети и без БД: транспорт (`requests.post`) в тестах клиента
подменяется, никакого похода к реальному серверу нет.

Зависимости из `requirements.txt` (`pydantic`, `requests`) нужны, чтобы
тест вообще импортировался — в этом окружении их ставит `pip install -r
requirements.txt` (или `uv pip install -r requirements.txt`) в venv.

## Чего здесь нет и не будет

- **Прямого доступа к БД.** Единственный способ службы что-либо записать
  на стороне victory62 — вебхук. Ни SQL, ни ActiveRecord, ни чтения
  Rails-таблиц напрямую.
- **Импорта Rails-кода и соседних `services/`.** Связь с приложением
  только через HTTP-контракт вебхука.
- **Решения о том, что применить к карточке ЖК.** Это делает
  `Zhk::Ingest` на Rails-стороне; служба отдаёт сырое наблюдение и
  получает построчный отчёт.
