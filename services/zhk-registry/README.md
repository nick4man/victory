# zhk-registry

Питоновская сторона «Реестра новостроек Рязани». Собирает наблюдения об
объектах в открытых источниках (ЕРЗ, сайты застройщиков, агрегаторы) и
отправляет их на вход Rails-стороны, которая уже сопоставляет наблюдение с
карточкой ЖК, пишет провенанс и раскладывает противоречивые поля в очередь
расхождений для редактора.

Продюсер для эндпоинта
`app/controllers/webhooks/zhk_ingest_controller.rb` из этого же
репозитория.

## Что здесь есть сейчас

Контракт, клиент отправки, два источника (ЕРЗ и сайт застройщика
«Единство») и крон-оркестратор, который сводит их вместе:

| Файл | Что |
|---|---|
| `observation.py` | `Observation` (pydantic) — форма одного наблюдения и её валидация. `to_payload()` отдаёт JSON ровно в форме, которую ждёт вебхук |
| `client.py` | `IngestClient` — шлёт наблюдения на `POST /webhooks/zhk_ingest`, режет батч по 50 сам, до отказа сервера не доводит |
| `sources/base.py` | Протокол `Source` (`discover`/`enrich`) и `polite_get` — вежливый GET с паузой и представленным User-Agent, общие для всех адаптеров |
| `sources/erz.py` | `ErzSource` — обнаружение ЖК Рязани и разбор карточки на erzrf.ru. Вес источника — 2 (агрегатор, вторичный) |
| `sources/edinstvo.py` | `EdinstvoSource` — карточки ЖК на сайте застройщика «Единство». Вес — 3 (первичный источник по своим объектам) |
| `run.py` | Точка входа крона: обходит источники по очереди, изолирует падение каждого, ретраит транзиентные сбои отправки, шлёт сводку прогона. Ставится в крон `crontab.example` |

### ЕРЗ.РФ — что реально можно снять без JavaScript

erzrf.ru — Angular SPA, и его `serverApp-state` (для гидратации) на живых
страницах всегда пустой JSON — сервер не рендерит в него данные
предметных виджетов. Отсюда разделение фактов по двум страницам:

- страница списка региона отдаёт статикой название, ссылку, этажность и
  срок сдачи по ЖК — их собирает `ErzSource.discover()`;
- карточка ЖК отдаёт статикой только «паспортную» таблицу (регион,
  населённый пункт, застройщик, улица) — их собирает `ErzSource.enrich()`
  через `parse_card()`.

`enrich()` переносит найденное в `discover()` (этажность, срок сдачи) в
итоговое наблюдение как есть, без нормализации — «III кв. 2026»,
«IV кв. 2026» и «Сдан» остаются в исходном виде: сравнивать такие записи
между собой — работа Rails-стороны.

## Контракт — общий с Rails, а не свой

`Observation` обязана парсить
`spec/fixtures/zhk/observation_example.json` — этот файл лежит в
Rails-дереве и используется и `spec/requests/webhooks/zhk_ingest_controller_spec.rb`,
и тестами этой службы. Если образец правят на одной стороне, тесты обеих
сторон обязаны упасть одновременно — иначе контракт разъезжается молча.

Поля наблюдения:

```json
{
  "source": "erz",
  "url": "https://erzrf.ru/novostroyki/zhk-skobelev-564336001",
  "external_id": "erz:564336001",
  "fetched_at": "2026-09-07T05:00:00Z",
  "name": "Скобелев",
  "city": "Рязань",
  "fields": { "developer": "Единство", "built_to": 2022 },
  "price": { "kind": "from", "price_per_sqm": 65000, "rooms": null }
}
```

`source` + `external_id` вместе — внешний идентификатор наблюдения,
которым Rails-сторона ловит дубликаты и обновления.

## Батч режется здесь, не на сервере

Вебхук отвергает батч длиннее 50 наблюдений целиком (422) — это защита
сервера, а не то, на что клиенту стоит полагаться. `IngestClient.send`
режет список на куски по 50 сам и шлёт их последовательными запросами;
до отказа `422 batch_too_large` доводить нельзя.

## Смысл кодов ответа для клиента

Построчный `status` в `results` и HTTP-код запроса значат разное, и
путать их нельзя:

| Что | Значит |
|---|---|
| `status: invalid` у наблюдения | не примем никогда, ретраить бессмысленно |
| `status: duplicate` | уже есть, всё хорошо, не ошибка |
| HTTP 4xx на весь запрос | вина запроса (плохой токен, батч не по контракту) |
| HTTP 503 | секрет `ZHK_INGEST_TOKEN` не выставлен на сервере — это поломка конфигурации Rails-стороны, а не отказ навсегда; такой запрос стоит повторить позже |

## Оркестратор и сводка прогона

`run.py` обходит источники ПО ОЧЕРЕДИ и изолирует падение каждого:
упавший ЕРЗ (недоступен `discover()`, отправка не восстановилась даже
после ретраев) не мешает обойти «Единство» следом. Транзиентные сбои
(HTTP 5xx, обрыв сети) ретраятся на трёх уровнях — `discover()`,
отправка батча, POST сводки — общим ретрай-циклом `call_with_retry`;
`invalid`-ответ и HTTP 4xx не ретраятся никогда, см. докстринги
`is_transient`/`call_with_retry`. `count` источника — это число
наблюдений, которые сервер РЕАЛЬНО применил (`status != invalid`), а не
просто сколько было отправлено: батч, отвергнутый целиком, не должен
выглядеть в сводке как полный успех.

После обхода всех источников (успешных и упавших) `run.py` шлёт
`POST /webhooks/zhk_ingest/summary` с `{"counts": {"erz": N,
"developer_site": M}}`. На Rails-стороне `Zhk::RunSummary` пишет каждое
число в журнал `ZhkIngestRun` и сравнивает его с ПРЕДЫДУЩИМ прогоном
того же источника (не с числом строк `zhk_observations` — тот считает
только новый/изменившийся контент и почти всегда околонулевой на
статичном каталоге, см. докстринг миграции
`db/migrate/*_create_zhk_ingest_runs.rb`). Источник помечается
молчащим, если он отдал кратно (порог — 30%) меньше предыдущего раза —
это детектор источника, который не упал явно, а просто перестал
что-либо находить (переверстка сайта, бан User-Agent). Подробности
решения «сколько молчаний считать сбоем» — в докстринге
`app/services/zhk/run_summary.rb`.

Ответ сервера несёт `delivered: true/false` — принят запрос ещё не
значит, что сводка дошла до сотрудников в Telegram (`TELEGRAM_STAFF_CHAT_ID`
может быть не настроен, сам Telegram — недоступен). `run.py` завершается
ненулевым кодом, если `delivered` не `true` — единственный способ, которым
полный отказ сводки заметит `MAILTO` крона, а не тишина.

Расписание — `crontab.example` (раз в неделю, с `flock -n` от наложения
прогонов).

## Запуск тестов

```bash
cd services/zhk-registry && python3 -m unittest discover -v
```

Без сети и без БД: транспорт (`requests.post`) в тестах клиента
подменяется, никакого похода к реальному серверу нет.

Зависимости из `requirements.txt` (`pydantic`, `requests`) нужны, чтобы
тест вообще импортировался — в этом окружении их ставит `pip install -r
requirements.txt` (или `uv pip install -r requirements.txt`) в venv.

## Чего здесь нет и не будет

- **Прямого доступа к БД.** Единственный способ службы что-либо записать
  на стороне victory62 — вебхук. Ни SQL, ни ActiveRecord, ни чтения
  Rails-таблиц напрямую.
- **Импорта Rails-кода и соседних `services/`.** Связь с приложением
  только через HTTP-контракт вебхука.
- **Решения о том, что применить к карточке ЖК.** Это делает
  `Zhk::Ingest` на Rails-стороне; служба отдаёт сырое наблюдение и
  получает построчный отчёт.
