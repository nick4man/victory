# CLAUDE.md — urgent-news-collector

Python-конвейер новостей внутри Rails-репозитория. Всё здесь устроено иначе, чем в
остальном `victory`. Корневой `CLAUDE.md` и skill `victory-rails-conventions` сюда
**не применяются** — из трёх жёстких правил репозитория едет только одно: даты `dd.MM.yy`.

## Чем отличается от Rails-части

| | Здесь |
|---|---|
| Язык, зависимости | Python + `pip` + `venv`, пины в `requirements.txt`. Не bundler, не `mise.toml` (python там не объявлен) |
| Стиль | двойные кавычки, type hints, `from __future__ import annotations` — противоположность `.rubocop.yml` |
| Тесты | stdlib `unittest`. Ни pytest, ни rspec |
| Расписание | системный crontab (`crontab.example`). **Не** Sidekiq-cron Rails-стороны |

🚨 Не добавляй задачи этого сервиса в расписание Rails (`config/sidekiq_cron.yml`):
служба живёт вне Rails и запускается своим кроном, см. `crontab.example`.

## Запуск тестов

```bash
python3 -m unittest test_urgent_relevance test_classify_retry test_model_chains test_chains_config test_free_model_probe -v   # 79 тестов, без сети и БД
```

Только **из каталога сервиса**: импорты плоские (`from urgent_relevance import ...`),
модули находят друг друга как соседи. Из корня репозитория не сработает.

`.venv` в репозитории нет — тесты гоняются системным `python3`, потому что
`urgent_relevance` и `classify_retry` не тянут ничего кроме stdlib. Виртуалка с `requirements.txt` нужна только
для самого конвейера (`urgent_collector` / `urgent_trigger`: feedparser, psycopg2, requests).

## Две чужие БД

- `NEWS_DB_*` — порт **5433**, pgvector, таблица `urgent_events`.
- `DB_*` — прод, `posts_queue` и `system_flags`.

Если `NEWS_DB_*` пусты, код падает обратно на `DB_*`. Ни одна из этих БД **не описана
миграциями в `db/migrate`** и не совпадает с `docker-compose.yml`. Увидев `urgent_events`,
не считай её забытой таблицей и не генерируй Rails-миграцию. В прод-БД колонки embedding
нет вовсе — там alpine postgres без pgvector.

## Где боевой код

```
исходник   services/urgent-news-collector/   ← этот каталог
боевой     /opt/victory-conveyor/            ← крон запускает отсюда
```

Выкатка — только `./deploy.sh` (`git fetch` + `git archive` из `origin/main`; локальный
`main` в main checkout сам не двигается и отстаёт). Правки прямо в боевом
каталоге затрёт следующий деплой.

История в два шага. 07.09.26 (#40) архивом объявили **репозиторий** openclaw, а
каталог `workspace-conveyor/IT/scripts` оставили боевым — целью выкладки.
11.09.26 архивом объявлен и **каталог**: `/opt/.openclaw/.openclaw/**` только на
чтение, писать нельзя, `sync-check.sh` отключён. Пути наружу сняты с кода и
собраны под `CONVEYOR_HOME` (env, дефолт `/opt/victory-conveyor`): `logs/`,
`notifications/`, `published/`, зеркало.

⚠️ `CONVEYOR_HOME` читается уже после загрузки `.env`, а `MIRROR_SCRIPT` и
`NOTIFICATIONS_DIR` в `pipeline_utils.py` — функции, а не константы. Если
вернёшь их на уровень модуля, значение из `.env` снова начнёт молча
игнорироваться: вызывающие скрипты грузят `.env` уже после `import`.

Зеркалирование на сайт идёт **внешним** скриптом по `MIRROR_SCRIPT` — он
принадлежит службе chat-host-cron и в боевом каталоге должен лежать рядом.
Связь с ним — контракт «исполняемый файл по пути», а не импорт: службы друг о
друге не знают, это проверяет `bin/services-check`. Без него зеркало молча
возвращает `None`, и посты уходят с fallback-URL.

## Что нельзя трогать «на глаз»

- **Порог дедупа 0.92** и якоря только по `published_to_tg = TRUE`. Порог 0.85 резал валидные
  новости: на коротких русских официальных заголовках baseline сам по себе ~0.85+. Без привязки
  к `published_to_tg` зарезанные события становились якорями для следующих — это стоило 4 дней
  тишины и ~31 потерянного события.
- **`URGENT_ELIGIBLE_TYPES` — ровно пять типов.** `MACRO_ECONOMICS` и `FX_RATE` исключены по
  замеру: 84 срочные публикации за 30 дней против 14.
- **Порядок цепочки `main` в `chains.json`** (с 13.10.26 цепочки живут там, а не в
  `pipeline_utils.py` — см. раздел ниже): сначала бесплатные, платный
  `anthropic/claude-sonnet-4` последний и помечен `"paid": true`. Подняв его выше, ты включишь
  платную модель на кроне каждые 15 минут, молча.
- **Две цепочки, а не одна** (с 13.09.26). Классификатор (`urgent_collector`) идёт по
  `CLASSIFIER_CHAIN` — это `main` из `chains.json` плюс бесплатные модели прямого
  OpenRouter (секция `classifier_extra`) сразу после Google и **без платного Sonnet**
  (с 02.10.26):
  за 10 дней он классифицировал 670 новостей и выбрал месячный лимит общего ключа, после
  чего неделю не было платного резерва и у постов. Не возвращай его в классификатор —
  `test_model_chains` это проверяет. Посты и дайджест идут по `MAIN_MODEL_CHAIN`
  без них: на промпте поста бесплатные модели мешали русский с английским и выдумывали
  цифры. Не переноси их в `main` — `test_model_chains` это проверяет.
  Бесплатным моделям OpenRouter нужен `reasoning: {enabled: false}`, иначе рассуждение
  съедает `max_tokens` и ответ приходит пустым.
- **`URGENT_COLLECTOR_MODEL` / `URGENT_TRIGGER_MODEL` / `OMNIROUTE_MODEL` в `.env`.**
  Это не «добавить модель», а схлопнуть всю цепочку в один маршрут без фолбэка
  (`urgent_collector.py:303`). 07.09.26 туда прописали `cc/claude-sonnet-4-5`, у
  которого в omniroute нет кредов — конвейер встал на 4 дня, 1950 новостей ушли
  в `NOISE` без классификации, и переклассифицировать их уже нельзя
  (`already_seen` режет по `source_url`).
- **Сбой классификатора ≠ NOISE** (с 13.09.26, `classify_retry.py`). Новость, на
  которой упала цепочка, не пишется в `urgent_events` и ждёт следующего прогона;
  `state/classifier_pending.json` в боевом каталоге помнит время первого сбоя. В
  NOISE по-старому она уходит только через 6 ч — страховка от «ядовитой» записи,
  которая гоняла бы цепочку вечно. Два сбоя подряд останавливают
  весь прогон, чтобы не жечь квоту на остальные новости. Вернёшь запись в NOISE
  при ошибке — повторишь потерю 1950 новостей 07.09.26.

## Цепочки моделей: chains.json, пробер, бюджет (13.10.26)

Источник цепочек — `chains.json`, а не код. `MAIN_MODEL_CHAIN` /
`FREE_CLASSIFIER_MODELS` / `PAID_MODELS` в `pipeline_utils.py` — уже
материализованный конфиг, править их там бессмысленно. Порядок поиска файла
(`resolve_chains_json_path`; переезд 1.0 добавил вариант 2):

1. env `CHAINS_JSON_PATH`;
2. `$CONVEYOR_HOME/state/chains.json`, если существует — оверрайд пробера на
   постоянном томе (docker: volume `conveyor_state` → `/opt/conveyor/state`),
   переживает rollout образа. Принадлежит проберу: руками не редактировать,
   удалить = вернуться к бандленному;
3. `$CONVEYOR_HOME/chains.json`, если существует (оверрайд на хосте; в
   контейнере это тот же файл, что и п.4 — `WORKDIR == CONVEYOR_HOME`);
4. `chains.json` рядом с `pipeline_utils.py` — едет в образ/деплой вместе
   с кодом, основной способ править вручную (через git);
5. встроенные дефолты `_DEFAULT_*` — на битый или отсутствующий файл: warning
   в лог и дефолты, исключений нет.

Пробер ЧИТАЕТ действующий конфиг (порядок выше), а ПИШЕТ всегда в
`state/chains.json` (`resolve_chains_json_write_path`) — иначе в контейнере
его правки лежали бы в слое образа и стирались бы следующим rollout.

⚠️ Конфиг читается один раз **при импорте** `pipeline_utils`, а `.env` скрипты
подтягивают уже после `import`. Поэтому оверрайды через `$CONVEYOR_HOME/...`
сработают, только если `CONVEYOR_HOME` задан в окружении cron-задачи, а не в
`.env` (в docker-образе он задан через `ENV CONVEYOR_HOME=/opt/conveyor` —
там работает всегда). Файл рядом с кодом (вариант 4) от этого не зависит.

⚠️ Docker (профиль `conveyor`, переезд 1.0): расписание — `crontab.docker`
(supercronic), а не crontab хоста; `OMNIROUTE_BASE_URL` обязан быть LAN-адресом
omniroute (он остаётся на chat, порт 20128), а не 127.0.0.1; фолбэка ключей
на `openclaw.json` в контейнере нет — все ключи только из `.env.conveyor`.

Формат: секции `main` и `classifier_extra`, записи
`{provider, model, timeout_s, paid, added_by?}`. Платные помечаются
`"paid": true` и собираются в `PAID_MODELS`. Платная запись в `classifier_extra`
в цепочку классификатора не попадёт: инвариант «в классификаторе платных нет»
(02.10.26) важнее конфига, запись лишь уезжает в `PAID_MODELS` с warning.

- **Телеметрия.** Каждая попытка вызова (успех/провал/сброс по бюджету) — одна
  JSON-строка в `llm_usage.jsonl` (env `LLM_USAGE_LOG`, дефолт
  `$CONVEYOR_HOME/logs/llm_usage.jsonl`). Best-effort: ошибка записи не роняет
  конвейер. По этому логу считается, какие звенья реально работают.
- **Бюджет платных.** `PAID_DAILY_LIMIT`=5, `PAID_MONTHLY_LIMIT`=20; счётчик в
  `$CONVEYOR_HOME/state/paid_budget.json` (`PAID_BUDGET_STATE_PATH`). Исчерпание
  бюджета = paid-звено пропускается. При успешном платном вызове и при исчерпании
  бюджета — DM главреду (`CHANNEL_BOT_TOKEN` + `CHIEF_EDITOR_CHAT_ID`, без них —
  молча). Мотив тот же, что у истории 13.09–22.09: Sonnet выбрал месячный лимит
  ключа за 10 дней — платный резерв должен быть ограничен сам по себе.
- **Автопробер** `free_model_probe.py` (cron: пн 05:40, `flock -n`) проверяет
  кандидатов из `probe_candidates.json` и живость бесплатных звеньев: классификатор —
  эталонными кейсами реальным промптом из `urgent_collector.py` (извлекается AST-ом),
  генерация — с эвристиками брака (латиница, выдуманные цифры, длина). State
  `$CONVEYOR_HOME/state/probe_state.json`: 3 подряд провала → disabled, 2 подряд
  успеха → enabled. `chains.json` обновляет атомарно и трогает только записи
  `added_by: "probe"` — ручные и платные никогда; both-кандидаты встают в `main`
  строго перед платным хвостом. CLI: `--dry-run`, `--only provider/model`, `--limit N`.
- **Сводка расхода** `llm_usage_report.py` (cron: пн 06:10, `--days 7 --telegram`,
  после пробера): доля бесплатных вызовов, разбивка по моделям/цепочкам, сработки
  платного хвоста, отказы по бюджету, топ ошибок. Краткая версия уходит главреду.

Целевая метрика системы: **≥99% вызовов бесплатные, платный хвост ≤2 сработок
в месяц**. Хуже — разбираться по `llm_usage.jsonl`, что за звенья отвалились.
