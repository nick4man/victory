# tg-test-observer — спецификация

⚠️ Как и остальные файлы в `.claude/agents/`, это **не** зарегистрированный `subagent_type`.
Запуск: `Agent(subagent_type: 'general-purpose', run_in_background: true)` с промптом
«выполняй `.claude/agents/tg-test-observer.md`, run_id = …».

## 1. Назначение и границы

Цель: за всё время сессии тестирования иметь **полный, воспроизводимый журнал** диалога
с ботом и **список аномалий с доказательствами**, не полагаясь на внимательность тестировщика.

Наблюдатель **только читает**. Жёсткие запреты:

| Нельзя | Почему |
|---|---|
| Отправлять сообщения, нажимать inline-кнопки, ставить реакции | Бот боевой (`victory62.org`), любое действие меняет CRM |
| Трогать другие вкладки Brave | Там госуслуги, почта, менеджер паролей |
| Навигировать/скроллить вкладку Telegram | Мешает тестировщику, сбивает виртуализацию ленты |
| Писать в репозиторий вне `tmp/tg-test-runs/` | Каталог в `.gitignore` (`/tmp/*`) |
| Сохранять токены, cookies, `localStorage` Telegram | Это сессия аккаунта |

## 2. Архитектура: коллектор + аналитик

LLM-агент не умеет непрерывно опрашивать страницу, а сырая лента быстро съест контекст.
Поэтому две части:

```
Brave (127.0.0.1:9222, только WS)                tmp/tg-test-runs/<run_id>/
  └─ вкладка web.telegram.org/k/#@anvictorybot     ├─ events.jsonl     ← коллектор
        │  MutationObserver + Runtime.addBinding   ├─ steps.jsonl      ← основная сессия
        ▼                                          ├─ anomalies.jsonl  ← аналитик
  collector (фоновый процесс, Python/Node)  ──────►├─ screenshots/
                                                   ├─ heartbeat.json   ← коллектор
  analyzer (этот агент, цикл раз в 30–60 с) ──────►└─ report.md        ← аналитик, в конце
```

### 2.1 Коллектор (`tmp/tg-test-runs/collector.py` или `.mjs`)

- **Подключение.** HTTP `/json/*` у этого Brave отдаёт 404, отладка включена через
  `chrome://inspect`. WS-адрес брать из
  `%LOCALAPPDATA%\BraveSoftware\Brave-Browser\User Data\DevToolsActivePort`
  (строка 1 — порт, строка 2 — путь). Своя CDP-сессия: `Target.attachToTarget(flatten)` на таргет,
  у которого `url` начинается с `https://web.telegram.org/` и содержит `@anvictorybot`.
  Сессию browser-use не переиспользовать и не закрывать.
- **Захват ленты.** В страницу через `Runtime.addBinding('__tgObs')` +
  `Runtime.evaluate` ставится `MutationObserver` на контейнер ленты. Подтверждённые
  селекторы Telegram Web K (проверено 13.09.26):
  - пузырь: `.bubble[data-mid]`, время: `data-timestamp` (unix, сек);
  - направление: класс `is-in` (бот) / `is-out` (мы);
  - текст: `.message` → `innerText` (хвост с временем `HH:MM` отрезать);
  - inline-кнопки: `.reply-markup-button` (текст каждой);
  - заголовок чата: `.chat-info .peer-title`.
  Селекторы проверять при старте; если `.bubble[data-mid]` не найден — событие
  `collector_error` и выход с кодом 2, не угадывать.
- **Дедупликация.** Лента виртуализирована: пузыри исчезают и появляются при скролле.
  Ключ — `data-mid`. Первое появление → `message_in`/`message_out`; повторное с другим
  хэшем текста или набора кнопок → `message_edited`; удаление узла **не** считать удалением
  сообщения (только если `mid` пропал и не вернулся при следующем полном снимке — `message_maybe_deleted`).
- **Полный снимок** последних 50 пузырей раз в 60 с — страховка от пропущенных мутаций.
- **Фон страницы:** `Runtime.consoleAPICalled` (level error), `Runtime.exceptionThrown`,
  `Network.loadingFailed` — только для этой вкладки; смена заголовка чата (тестировщик
  ушёл из диалога) → `chat_switched`; индикатор «Connecting…/Waiting for network» → `tg_offline`.
- **Скриншоты** по запросу аналитика: `Page.captureScreenshot` этой вкладки →
  `screenshots/<anomaly_id>.png`. Без активации вкладки.
- `heartbeat.json` раз в 15 с: `{ts, last_mid, events_written, attached: true}`.
- Запуск — фоново (`run_in_background`), остановка — файл `STOP` в каталоге прогона.

### 2.2 Основная сессия пишет шаги (`steps.jsonl`)

Без шагов нельзя отличить «бот молчит» от «ничего не спрашивали». **Перед** каждой отправкой
тестировщик (основная сессия Claude) дописывает строку:

```json
{"step_id":"A3","ts":1789275900,"sent":"/help","group":"A","role":"director",
 "expect":{"reply":true,"max_latency_s":10,"contains":["Команды Виктори-бота"],
           "buttons":null,"silent_ok":false},"note":"playbook A3"}
```

`expect.silent_ok: true` — для сценариев, где молчание верно (спам C2, `ping` от не-сотрудника).
Нажатие inline-кнопки — тоже шаг: `"sent":"[btn] ▶ Начать"`.

### 2.3 Аналитик (этот агент)

Цикл раз в 30–60 с (`ScheduleWakeup`/`Monitor` в основной сессии либо sleep-цикл в фоновом агенте):

1. Проверить `heartbeat.json`: старше 45 с → аномалия `OBS-01`.
2. Дочитать новые строки `events.jsonl` и `steps.jsonl` (хранить смещения в `analyzer_state.json`).
3. Сопоставить события с шагами: ответ шага = входящие `is-in` в окне
   `[step.ts, следующий step.ts или step.ts + 120 с]`.
4. Прогнать детекторы (§4), записать новые аномалии, запросить скриншот для S1/S2.
5. S1 — сразу сообщить основной сессии (`SendMessage`, иначе строка в `ALERT.md`).

## 3. Схемы логов

`events.jsonl` — одна строка на событие:

```json
{"ts":1789275904,"seen_at":1789275904.8,"type":"message_in","mid":"72479",
 "reply_to_mid":"72478","text":"Команды Виктори-бота…","text_sha1":"…","len":2210,
 "buttons":[],"html_flags":{"has_pre":true,"has_link":false}}
```

Типы: `message_in`, `message_out`, `message_edited`, `message_maybe_deleted`,
`buttons_changed`, `chat_switched`, `tg_offline`, `tg_online`, `console_error`,
`js_exception`, `network_failed`, `snapshot`, `collector_error`.

`anomalies.jsonl`:

```json
{"id":"AN-0007","ts":1789275990,"rule":"BOT-02","severity":"S2","step_id":"E1",
 "mids":["72490"],"summary":"В ответе ISO-дата 2026-09-13 вместо 13.09.26",
 "evidence":"…до 2026-09-13 18:00…","screenshot":"screenshots/AN-0007.png",
 "status":"open"}
```

`status`: `open` → `confirmed` (подтвердил тестировщик) / `dismissed` (с полем `reason`).

## 4. Каталог аномалий

Серьёзность: **S1** — сломан сценарий или риск для данных/ПДн, сообщить немедленно;
**S2** — неверное поведение, сценарий проходит; **S3** — косметика; **INFO** — к сведению.

| ID | Что | Правило детекции | Sev |
|---|---|---|---|
| BOT-01 | Нет ответа | шаг с `reply:true`, нет `is-in` за 60 с (варн на `max_latency_s`) | S1 / S2 |
| BOT-02 | Неверный формат даты | в тексте бота `\b\d{4}-\d{2}-\d{2}\b`, `\b\d{1,2}/\d{1,2}/\d{2,4}\b`, `T\d{2}:\d{2}` — правило проекта `dd.MM.yy` | S2 |
| BOT-03 | Утечка ошибки | `undefined method`, `NoMethodError`, `nil`, `Traceback`, `Exception`, `#<[A-Z]\w+`, `500`, `translation missing`, `SQL`, `PG::` | S1 |
| BOT-04 | Утечка разметки | сырые `<b>`, `</i>`, `&lt;`, `&amp;`, `**`, `__`, `%{`, `#{`, `{{` в видимом тексте | S2 |
| BOT-05 | Дубль ответа | два `is-in` с одинаковым `text_sha1` в пределах 15 с | S2 |
| BOT-06 | Незапрошенное сообщение | `is-in` вне окна любого шага. Если время совпадает с кроном из `config/sidekiq_cron.yml` (дайджесты 08:00/10:00/18:00 MSK) — INFO, иначе S3 | INFO / S3 |
| BOT-07 | Несоответствие ожиданию | нет ни одной подстроки из `expect.contains`, или кнопки ≠ `expect.buttons` | S2 |
| BOT-08 | Ответ на «молчаливый» шаг | `silent_ok:true`, но пришёл `is-in` | S2 |
| BOT-09 | Ролевая утечка | роль шага `agent`/`client`, а в ответе команды из блоков «Руководителям»/«Директору» | S1 |
| BOT-10 | ПДн в открытом виде | телефон `\+?7\d{10}`, паспорт `\d{4}\s?\d{6}`, e-mail — в ответе, где их не просили | S2 (в логах маскировать, см. §6) |
| BOT-11 | Обрезка / лимит | `len ≥ 4000` или текст кончается на `…` без закрывающей структуры | S3 |
| BOT-12 | Непереведённое | ≥ 3 подряд англ. слов вне команд/кода, `TODO`, `lorem`, `FIXME` | S3 |
| BOT-13 | Кнопки пропали/изменились сами | `buttons_changed` без шага-нажатия в последние 10 с | S3 |
| BOT-14 | Кнопка не отработала | шаг `[btn] …`, за 15 с нет ни `message_edited`, ни нового `is-in` | S2 |
| BOT-15 | Команда из `/help` неизвестна боту | ответ содержит «неизвестн»/«не понимаю» на команду, которая есть в последнем `/help` | S2 |
| BOT-16 | Регресс латентности | медиана задержки по группе шагов > 2× медианы первых 5 шагов прогона | INFO |
| BOT-17 | Лимит клиента | `rate limit`/«слишком много» — сверить со счётчиком (10 сообщений/час на tg_user_id) | INFO |
| OBS-01 | Коллектор умер | `heartbeat.json` старше 45 с | S1 |
| OBS-02 | Тестировщик вне диалога | `chat_switched` — события до возврата не сопоставлять | INFO |
| OBS-03 | Нет сети Telegram | `tg_offline` > 10 с; BOT-01 за этот интервал не поднимать | INFO |
| OBS-04 | Ошибки клиента TG Web | `js_exception`/`network_failed` к `*.telegram.org` ≥ 3 за минуту | S3 |

Контекст, который **снижает** серьёзность, а не глушит аномалию: тихие часы 21:00–07:00 MSK и
выходные (многие DM-потоки намеренно молчат — см. `live-test-playbook.md` → Notes).

## 5. Отчётность

- **Во время прогона** — только S1 сразу; остальное копится.
- **По запросу «статус наблюдателя»** — 5 строк: живость коллектора, шагов/сообщений, открытые S1/S2.
- **В конце** (`STOP` или команда) — `report.md`:
  1. Шапка: run_id, период `dd.MM.yy HH:MM–HH:MM`, роль аккаунта, шагов, сообщений бота.
  2. Таблица аномалий по серьёзности: ID, правило, шаг, краткое описание, скриншот.
  3. Латентность: медиана / p90 / max по группам плейбука.
  4. Шаги без вердикта (нет ответа и нет `silent_ok`) — отдельным списком.
  5. Кандидаты в баги: для S1/S2 — предполагаемое место в коде
     (`app/services/telegram/work_bot/router.rb`, `commands/*`, `callbacks_router.rb`,
     `client_bot/*`, `inbound_processor.rb`) — только гипотеза, помечать как «не проверено».

Все даты в отчёте и сообщениях — `dd.MM.yy`.

## 6. Приватность

- Логируется **только** диалог с `@anvictorybot` (и рабочая группа — лишь если тестировщик
  явно добавил её `chat` в `run.json`).
- В `events.jsonl` телефоны маскируются до `+7******NN`, e-mail до `a***@domain`, номера
  документов — полностью `[DOC]`. Сырые значения в памяти коллектора не удерживать.
- Скриншоты — только вкладки Telegram; каталог прогона не публиковать и не пушить.

## 7. Жизненный цикл

1. Основная сессия создаёт `tmp/tg-test-runs/<yyMMdd-HHmm>/run.json`:
   `{run_id, tester_role, bot:"@anvictorybot", playbook:".claude/docs/live-test-playbook.md", started_at}`.
2. Запуск коллектора в фоне; дождаться `heartbeat.json` и события `snapshot`.
3. Запуск аналитика (фоновый агент) с `run_id`.
4. Тест: шаг → запись в `steps.jsonl` → отправка → следующий шаг.
5. Стоп: файл `STOP` → коллектор пишет финальный `snapshot` и выходит → аналитик
   добивает хвост, пишет `report.md`, возвращает основной сессии сводку S1/S2.

## 8. Критерии приёмки реализации

- [ ] Коллектор цепляется по WS из `DevToolsActivePort`, не ломая сессию browser-use.
- [ ] Отправка `/help` вручную даёт в `events.jsonl` ровно один `message_out` и один `message_in` с тем же `mid`, что в DOM.
- [ ] Скролл ленты вверх-вниз не порождает дублей `message_in`.
- [ ] Шаг с `reply:true` без ответа (напр. отправка при выключенной сети) даёт `BOT-01` через 60 с.
- [ ] Синтетический текст с `2026-09-13` в тестовом `events.jsonl` даёт `BOT-02`.
- [ ] Убитый коллектор → `OBS-01` не позже чем через 60 с.
- [ ] В логах нет немаскированных телефонов и e-mail.
- [ ] Ни одного исходящего действия от наблюдателя (проверка: все `message_out` сопоставлены шагам).
