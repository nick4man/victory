API Сервиса Topnlab позволяет реализовать следующие действия:
```
 1. Получать id карточек объектов, заявок и услуг которые были созданы и/или
    отредактированы в Topnlab
 2. Метод для получения id карточек объектов, заявок и услуг из Topnlab для последующего
    запроса на получения данных по этим id
 3. Получать параметры объектов, заявок и услуг из Topnlab с помощью запросов к API
 4. Получать объекты МЛС из Topnlab
 5. Получать объекты Парсера из Topnlab
 6. Получать логи по объектам и заявкам и сконструированным сущностями.
 7. Редактировать значения сконструированных полей в карточках объектов, заявок и услуг
    (дефолтные поля редактировать нельзя)
 8. Получение списка пользователей
 9. Получение структуры компании: дерево пользователей и департаментов
10. Получение и отправка публичных примечаний по карточке
11. Получение списка настроенных стадий
```
## 1. Получать id карточек объектов, заявок и услуг, которые были
созданы и/или отредактированы в Topnlab
Если вам нужно получать из Topnlab события о создании или редактировании карточек вам
необходимо подготовить веб-адрес (ссылку), на который будет отправляться информация о
соответствующих событиях. Можно использовать один и тот же адрес для всех уведомлений, а
можно использовать разные адреса для разных события или типов карточек.
При создании\редактировании объектов Topnlab отправляет на ваш адрес POST-запрос c
параметрами
Формат передачи данных - application/x-www-form-urlencoded
В случае если ключ не подходит отправляется код ответа 403.
Если запрошенная запись не найдена, возвращается код ответа 404.

Для объектов: Продавцы, Арендодатели


```
id=123
type=realty
```
Для заявок: Покупатели, Арендаторы


```
id=123
type=order
```
Для услуговых заявок - это те что создаются в Topnlab в разделе "Конструктор заявок"

Дополнительно передается
```
   type_id - типа заявки (Например: 1800) этот идентификатор можно найти в Topnlab
   (Настройки системы --> Конструктор заявок) type_name - название типа заявки (Например:
   Ипотечная заявка)

id=123

 type=service
type_id=1800
type_name=Ипотечная заявка
```

```
n=sale&realty_type= flat&created=2022-10-01&in_ad=false&was_in_ad=true
```

Обязательных параметров всего два:
```

          order - Покупатели, Арендаторы, в том числе из раздела "Корзина"
          service - Услуговые заявки, в том числе из раздела "Корзина" (услуговые заявки - это те
          что создаются в Topnlab в разделе "Конструктор заявок")
```

С помощью дополнительных параметров вы можете добавлять условия поиска идентификаторов.

```
    2022-10-01 или 2022-10-01 12:20:20
    manual_update_from - выводит карточки, дата последнего действия с которыми была после
    указанной даты. Допустимые форматы даты: 2022-10-01 или 2022-10-01
    manual_update_to - выводит карточки, дата последнего действия с которыми была до
    указанной даты. Допустимые форматы даты: 2022-10-01 или 2022-10-01
    action - тип карточки (sale - продажа, rent - аренда, 1234 - id типа Услуговой заявки. )
    realty_type - тип недвижимости flat - квартира, room - комната, commerce - коммерция,
    house - загородка, land - участок, garage - машиноместо/гараж . Параметр не применим
    для услуговых заявок (type=service)
    stage_id - идентификатор стадии, выводит карточки на заданной стадии
    deal_state - статус карточки
          lead - Сбор данных​
          active - В работе
          ad - В рекламе​
          prepayment - Аванс
          denied - Отказ
          deal - Сделка
          deferred - Отложен
          archive - База лидов
          Параметры поиска можно скомбинировать, чтобы получить карточки разных статусов:
          deal_state[]=lead&deal_state[]=active&deal_state[]=ad
    in_ad Факт наличия в рекламе
    was_in_ad Был ли объект в рекламе
    is_feed - «Выводить в фид / выгрузка на сайт». Допустимые значения true или false.
```

## 3a. Realty `rooms` field — encoding (verified 18.05.26)

**Important:** в реалити-payload поле `rooms` — это НЕ литеральное число
комнат, а **enum-id** из словаря `/realty/getoptions['rooms']`. Каждое
значение — id в виде integer, кратное 10:

| Topnlab `rooms` id | Метка | Victory convention `rooms` |
|---|---|---|
| `10`  | Студия | `0`   |
| `20`  | 1 ком. | `1`   |
| `30`  | 2 ком. | `2`   |
| `40`  | 3 ком. | `3`   |
| `50`  | 4 ком. | `4`   |
| `60`  | 5 ком. | `5`   |
| `70`  | 6 ком. | `6`   |
| `80`..`200` | 7..19 ком. | `(id/10) − 1` |
| `205` | 20+ ком. | `20`  |
| `99`  | Свободная планировка | `nil` + label «Свободная планировка» |

Формула для большинства значений: `count = id / 10 − 1`. Особые случаи:
- `id=10` → 0 (студия по нашей convention в `Property#rooms_info`)
- `id=99` → free planning (не привязан к count'у)
- `id=205` → 20+ (cap at 20)

**Для `realty_type='room'`** (комната в общежитии/коммуналке) словарь
называется `rooms_for_room` — id=20→1 ком., id=30→2 ком., … id=100→9
ком., id=105→10+. Это означает «комната в N-комнатной квартире/общаге».
Используется параллельно с `room_type` (1=Общежитие, 2=Коммуналка,
3=Стандартная квартира).

**Доп. поля для верификации** (если `rooms` ambiguous):
- `area_room` — строка-сумма площадей комнат через `+` (e.g. `"15.3+12"`
  для 2-комн, `"17+13+12+10"` для 4-комн). Можно использовать как
  cross-check.
- `room_type` — тип жилья (см. enum выше).
- `rooms_deal` — деал-side поле где `id=0..19` буквально равно
  кол-ву комнат. Для realty payload обычно `null`.

**Bug we fixed 18.05.26:** старый `Topnlab::PropertyMapper#sane_rooms`
полагался на эвристику «rooms > 9 = студия» — что было неверно для ВСЕХ
realty (минимальный валидный id — 10 = студия). 101 property в проде
были mis-tagged как «Студия». Fix: переключение на enum-таблицу выше.
