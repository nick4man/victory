# Тест-план: конвейер сделок (Шаги 1–5)

Дата: 10.09.26 · Спутник [`DESIGN.md`](DESIGN.md) · Статус: проект

Что покрывать, каким типом теста и в каком порядке, чтобы четыре фазы дизайна ехали без регрессий.
Отдельно — дыры в текущем покрытии, найденные при разборе.

---

## 1. Исходное состояние

110 спек-файлов, 1102 примера, гоняются в CI (`lint.yml`, свой PostGIS+pgvector-образ, сеть закрыта
WebMock, ActiveJob на `:test`). SimpleCov не подключён — процент покрытия никто не меряет, поэтому
цели ниже сформулированы поведенчески, а не в процентах. Это осознанно: цифра, которую никто не
считает, — не цель.

### Дыры ровно там, куда едут фазы 1–2

| Область | Состояние | Почему это важно сейчас |
|---|---|---|
| `Property.in_advertising` | **ноль спек** | скоуп отбирает объекты для трёх публичных фидов; в нём живёт баг D1 |
| `Property#ready_for_site?` | **ноль спек** | вторая половина той же развилки видимости |
| `FeedsController` (`yrl`/`cian`/`avito`) | **ноль спек** | три публичных XML-эндпоинта без единого теста |
| `Nextcloud::DealFolderResolver` | **ноль спек** | чистая функция без побочных эффектов — идеальный кандидат, а покрытия нет |
| `Nextcloud::ShareLinkGenerator`, `Client` | **ноль спек** | фаза 2 будет на них опираться |
| `Telegram::WorkBot::Sla::PingService` | **ноль спек** | дедуп, quiet hours, guard неактивного исполнителя — вся логика непокрыта |
| `Task` | 60 строк: `created_by_tg`, `created_in`, `append_attachment!` | `overdue`, `due_today`, `suspicious_flag`, enums — не покрыты, а фаза 3 строится на них |

`spec/models/property_spec.rb` покрывает `.active`, `.published`, `.assigned_to`, `.unassigned` — но
не два предиката, которые решают, увидит ли объект внешний мир.

### Прецедент, который стоит скопировать

[`spec/requests/sitemap_spec.rb`](../../../spec/requests/sitemap_spec.rb) появилась по итогам ревью
PR #37 и в шапке описывает ровно наш случай: два потребителя одного состояния разошлись, а спеки
проверяли каждую сторону отдельно, поэтому расхождение дожило до ревью. Вывод оттуда переносится
дословно — **проверять согласованность двух потребителей, а не каждого по отдельности**.

Баг D1 той же природы: сайт объект прячет, фиды публикуют. Значит и тест должен быть про
согласованность, а не про каждый скоуп в изоляции.

## 2. Пирамида применительно к этому проекту

```
      /  E2E  \        нет и не нужно — внешние площадки не наши,
     /         \       контракт с ними = валидность XML
    / Request   \      фиды, вебхуки, публичные страницы — тонкий слой
   /             \
  /  Unit/Model   \    скоупы, резолверы, генераторы задач, SLA-логика
 /_________________\   ← основная масса
```

Слоя E2E здесь быть не должно: проверить «объявление исчезло с Авито» можно только у Авито, а это
не тест, а мониторинг. Граница ответственности — валидный XML с правильным набором объектов;
что площадка с ним сделает, мы не контролируем.

| Тип | Когда | Стоимость сопровождения |
|---|---|---|
| Model/unit | вся бизнес-логика: скоупы, `DealFolderResolver`, `TaskGenerator`, эскалационная лестница | низкая |
| Request | `FeedsController`, вебхуки | средняя — ломается при смене формата |
| Service + WebMock | `Nextcloud::Client`, `Topnlab::Client` | средняя |
| Job | `Sla::PingJob` (quiet hours, defer) | низкая, ActiveJob на `:test` |

## 3. План по фазам дизайна

### Фаза 1 — `prepayment` в `EXCLUDED_FROM_CATALOG`

Правка однострочная, поведение трёх публичных фидов меняется. Здесь TDD не ритуал, а
единственный способ не поменять заодно что-то ещё.

**Порядок:**

1. Спека, фиксирующая **текущее** поведение всех состояний `deal_state` в `in_advertising` — до
   правки, зелёная. Она же покажет, что ещё живёт в этом скоупе.
2. Красный пример на желаемое поведение `prepayment`.
3. Правка одной строки.
4. Спека согласованности: множество объектов на сайте и множество в фидах не должны противоречить
   друг другу.

**Что тестировать:**

| Что | Тип | Кейсы |
|---|---|---|
| `Property.in_advertising` | model | по одному примеру на каждое значение `deal_state` (`ad`, `active`, `lead`, `prepayment`, `deferred`, `deal`, `archive`, `denied`, `nil`) |
| То же, канал рекламы | model | `in_ad=true/in_mls=false`, `false/true`, `false/false`, оба `true` |
| То же, публикация | model | не `published` (нет `published_at` или `status != active`) → не попадает независимо от `deal_state` |
| `ready_for_site?` ↔ `in_advertising` | model | согласованность: объект, скрытый с сайта по `deal_state`, не должен оставаться в фидах |
| `GET /feeds/{yrl,cian,avito}.xml` | request | 200 + `application/xml`; `X-Robots-Tag: noindex, follow`; объект с `prepayment` отсутствует во всех трёх |
| Кэш и conditional GET | request | второй запрос с `If-None-Match` → 304 |

**Пример:**

```ruby
# spec/models/property_advertising_spec.rb
RSpec.describe Property, '.in_advertising' do
  # Таблица состояний — источник правды по видимости объекта во внешних фидах.
  # Значения deal_state приходят из Topnlab; список исключений — EXCLUDED_FROM_CATALOG.
  DEAL_STATES = {
    'ad'         => true,   # в рекламе — основной рабочий state
    'active'     => true,   # внутренний CRM state, но фиды его пускают
    'lead'       => true,
    'prepayment' => false,  # задаток принят → реклама останавливается (Шаг 5, п.6)
    'deferred'   => false,
    'deal'       => false,
    'archive'    => false,
    'denied'     => false,
    nil          => true    # неизвестное состояние не должно прятать объект
  }.freeze

  DEAL_STATES.each do |state, expected|
    it "#{expected ? 'включает' : 'исключает'} deal_state=#{state.inspect}" do
      property = create(:property, :on_site, :in_feeds, deal_state: state)
      expect(described_class.in_advertising).to send(expected ? :include : :not_include, property)
    end
  end
end

# spec/models/property_visibility_consistency_spec.rb
RSpec.describe Property, 'согласованность сайта и фидов' do
  # Урок sitemap_spec (PR #37): расхождение двух потребителей одного состояния
  # не ловится, пока каждого проверяют отдельно. Здесь спрашиваем обоих сразу.
  it 'не оставляет в фидах объект, скрытый с сайта по deal_state' do
    hidden_from_site = Property::IMPORT_DEAL_STATES - Property::PUBLISHABLE_DEAL_STATES

    hidden_from_site.each do |state|
      property = create(:property, :on_site, :in_feeds, deal_state: state)

      next if property.ready_for_site?

      expect(described_class.in_advertising).not_to include(property),
        "deal_state=#{state}: скрыт с сайта, но остаётся в XML-фидах"
    end
  end
end
```

⚠️ Второй пример намеренно написан как проверка инварианта, а не как список ожиданий: при появлении
нового `deal_state` он сработает сам, без правки спеки.

**Нужна фабричная трейта** — в `spec/factories/properties.rb` сейчас нет ни `deal_state`, ни
`in_ad`/`in_mls`:

```ruby
trait :in_feeds do
  in_ad { true }
  in_mls { false }
  deal_state { 'ad' }
end
```

**Открытый вопрос, который меняет ожидания теста.** Для Авито размещение платное и снимается
вручную, для `yrl`/`cian` — фидовое. Если решение агентства будет «Авито исключаем позже, чем
остальных», таблица состояний перестанет быть общей для трёх эндпоинтов, и request-спеки
разъедутся. До ответа тест пишется по общей таблице.

### Фаза 2 — структура Nextcloud

| Что | Тип | Кейсы |
|---|---|---|
| `DealFolderResolver.for` | unit (чистая функция, без сети) | каждый `property_type` → свой `TOP_FOLDER`; гео-сплит только для `flat`/`land`; `NO-ID` при пустом `external_id`; имя клиента опускается при `nil` inquiry |
| То же, гео | unit | 🔴 **регресс-тест на S4**: «Рязанская область, Шилово» не должен уезжать в `РЯЗАНЬ`; «Ленинградская область» не должна остаться без сплита |
| `ensure_structure!` | service + WebMock | идемпотентность (повторный вызов не падает); создание всех четырёх подпапок; частично существующая структура достраивается |
| То же, отказ | service + WebMock | Nextcloud вернул 5xx → шаг не блокируется, job уходит в retry |
| Кириллица в путях | unit | пробелы и «ё» в имени папки экранируются корректно |

`DealFolderResolver` — чистая функция, тестируется без сети и без БД (нужен только объект-двойник
`Property`). Это самый дешёвый тест во всём плане и самая заметная сейчас дыра.

### Фаза 3 — конвейер

| Что | Тип | Кейсы |
|---|---|---|
| `config/reglament_steps.yml` | schema-спека | все шаги имеют `title`, `tasks`, у каждой задачи валидные `kind` и `due_in`; `after` ссылается на существующий `key`. Прецедент — валидация `telegram_topics.yml` |
| `ListingPipeline#complete_step!` | model | двигает `current_step`; пишет `step_history`; **идемпотентность** — двойной клик по кнопке не создаёт два перехода |
| То же, порядок | model | нельзя завершить шаг, если остались открытые `required`-задачи |
| `TaskGenerator` | service | из YAML разворачивается ожидаемый набор `Task`; `due_at` считается от `step_entered_at`; `after:` считается от завершения зависимой задачи |
| Повторный запуск генератора | service | не плодит дубли задач для уже сгенерированного шага |
| `Task` (добор покрытия) | model | `overdue`, `due_today` на границе суток; `suspicious_flag` при закрытии call-задачи без `first_contact_at` |
| Кнопка/команда завершения | service | `task_action_callback` и `/step done` дают одинаковый результат |

Тест на границе суток для `due_today` — не педантизм: скоуп использует `Time.current.all_day`, а
контейнеры зависят от `TZ` (см. CLAUDE.md про два планировщика). Тест должен явно замораживать
время в MSK.

### Фаза 4 — SLA и отчётность

| Что | Тип | Кейсы |
|---|---|---|
| `Sla::PingService` (существующий) | service | 🔴 сейчас непокрыт: дедуп 30 мин; skip при пустом `assigned_to`; skip при закрытом лиде; эскалация при `assignee.status != 'active'` |
| Новые виды пинга | service | `:task_overdue` и `:step_overdue` не ломают дедуп существующего `:first_contact_overdue` |
| Эскалационная лестница | service | дедлайн → DM; +2 часа → #ДИСПЕТЧЕРСКАЯ; дедлайн шага → руководителю |
| Quiet hours | job | пинг в 22:00 переносится на 07:00; **блокер с «0 минут» уходит немедленно, игнорируя quiet hours** |
| Недельный дайджест | service | объект, зависший на шаге дольше `entry_deadline`, попадает в отчёт |

Исключение блокера из quiet hours — самый вероятный кандидат на регрессию при будущих правках
`QuietHours`, поэтому тест на него обязателен, а не желателен.

## 4. Целевые показатели

Вместо процентов — проверяемые утверждения. Каждое либо выполнено, либо нет:

1. Ни один публичный эндпоинт (`/feeds/*.xml`) не остаётся без request-спеки.
2. Каждое значение `deal_state` имеет явный пример в таблице видимости — новое значение без теста
   ронять сборку не должно, но и появляться незамеченным тоже.
3. Согласованность «сайт ↔ фиды» проверяется инвариантом, а не перечислением.
4. Каждая чистая функция без побочных эффектов (`DealFolderResolver`, `TaskGenerator`) покрыта
   unit-тестами без БД и сети.
5. Каждый внешний вызов (Nextcloud, Topnlab) имеет тест на путь отказа, а не только на успех.
6. Каждое исключение из общего правила (блокер вне quiet hours, `nil` deal_state как видимый)
   зафиксировано тестом с комментарием «почему», иначе следующий рефакторинг его снимет.

## 5. Что не тестировать

- **Валидность XML для конкретной площадки.** Это контракт площадки, он меняется без нашего ведома;
  проверять его тестом — ловить чужие изменения задним числом. Место для мониторинга, не для CI.
- **Работу самого Nextcloud/Topnlab.** Тестируем свой клиент и обработку ответов, не чужой сервер.
- **Формулировки текстов регламента.** Скрипты ответов клиентам меняются часто и по бизнес-причинам;
  тест на текст сообщения превратится в помеху при первой же правке. Тестировать надо факт отправки
  и адресата, не содержимое.
- **Генерацию превью для YouTube, обработку фото.** Ручные операции вне системы.

поменялось в поведении.

openclaw-машине Ruby нет — оттуда спеки не запускать и «зелёные» не докладывать.
