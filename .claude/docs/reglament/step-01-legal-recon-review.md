# Ревью регламента — Шаг 1 «Юридическая разведка»

Дата ревью: 10.09.26 · Предмет: [`step-01-legal-recon.md`](step-01-legal-recon.md)
Метод: сверка с фактической реализацией (`Nextcloud::DealFolderResolver`, `Topnlab::Client`,
дерево NC из `nextcloud-cheatsheet.md`, work-bot) + сквозная проверка стыка с [Шагом 2](step-02-staging-photo.md).

**Итог:** регламент заметно сильнее Шага 2 — исполнители разведены (руководитель/стажёр), тайминги
в минутах, есть красная кнопка с нулевым временем реакции, ловушки описаны через конкретный
триггер. Главная проблема не внутри, а на стыке: **описанная здесь структура папок не совпадает с
той, которую строит код**, и именно она объясняет блокер R1 из ревью Шага 2.

## 🔴 Blocking

### S1. Имя папки сделки конфликтует с `DealFolderResolver`

| | Схема |
|---|---|
| Регламент (Этап 1.2) | `[Номер из CRM]_ПРОДАЖА_[Название объекта]` — разделитель `_`, имени клиента нет |
| Код ([`deal_folder_resolver.rb`](../../../app/services/nextcloud/deal_folder_resolver.rb)) | `<TopnlabID> <ДЕЙСТВИЕ> <дескриптор> <ClientFirstName>` — разделитель пробел, имя клиента есть |

Пример из docstring резолвера: `128248561 ПРОДАЖА 2-ка Сенная Анна`. По регламенту стажёр создаст
`128248561_ПРОДАЖА_2-ка Сенная`. Это **две разные папки на один объект**: код не найдёт папку
стажёра (`Nextcloud::Client#exists?` вернёт false) и создаст свою. Дальше документы стажёра и файлы
бота живут раздельно, и ни один из двух наборов не полон.

**Рекомендация:** привести регламент к схеме кода (она уже в проде и умеет резолвиться из
`Property` автоматически), а не наоборот.

### S2. Подпапок `01_/02_` не существует — и это разгадка блокера Шага 2

Ни `01_Документы_по_объекту`, ни `02_Юридический_блок` не встречаются ни в дереве NC
(`nextcloud-cheatsheet.md`), ни в коде — grep даёт ноль. Резолвер строит **только** путь до папки
объекта, подпапки не создаёт.

При этом Шаг 2 требует класть исходники в `03_Фото_Видео / Исходники` — то есть **третью подпапку
той же нумерованной схемы**. В ревью Шага 2 (finding R1) этот путь был помечен как несуществующий;
теперь видно, что он не выдуман, а принадлежит схеме `01_/02_/03_`, которую Шаг 1 объявляет
ровно из двух элементов, а код не создаёт вовсе.

**Решение нужно одно на оба шага:**
1. Узаконить схему `01_Документы_по_объекту / 02_Юридический_блок / 03_Фото_Видео` как часть
   deal-folder convention.
2. Научить `DealFolderResolver` (или обёртку над `Nextcloud::Client`) создавать три подпапки при
   `ensure_folder!`, чтобы стажёру нечего было создавать руками.
3. Поправить Шаг 1 (создавать три, а не две) и Шаг 2 (полный путь вместо `03_Фото_Видео`).

### S3. Категории регламента не совпадают с верхними папками NC

Регламент объединяет «🏡 Дом и Земельный участок» в одну категорию. В NC и в коде это **разные**
top-folder с разным поведением: `house → ДОМА` (без гео-разбивки), `land → ЗЕМЛЯ` (с гео-разбивкой).
Для типовой сделки «дом с участком» регламент не даёт ответа, куда класть папку, а `TOP_FOLDER` не
имеет комбинированного значения. Остальные категории тоже названы в единственном числе
(«Квартира», «Гараж») против фактических `КВАРТИРЫ`, `ГАРАЖИ`.

## 🟡 Important

### S4. Регионы регламента шире, чем умеет код (дефект в коде, не в регламенте)

`GEO_PATTERNS` в резолвере — три правила:

```ruby
[/\bРяза/i, 'РЯЗАНЬ'], [/\bМоскв/i, 'МОСКВА'], [/Санкт.Петер|СПб/i, 'САНКТ-ПЕТЕРБУРГ']
```

- Адрес «Рязанская область, р.п. Шилово» матчится `/\bРяза/` → уедет в **РЯЗАНЬ**, хотя в NC есть
  отдельная `РЯЗАНСКАЯ ОБЛАСТЬ`. То же для Московской области.
- «Ленинградская область» из списка регламента не матчится ничем → гео-разбивки не будет вообще.

Регламент здесь прав, а код — нет. Стоит завести отдельную задачу на паттерны области-vs-город
(порядок правил важен: область должна проверяться раньше города).

### S5. Паспортные данные ложатся в свободно обходимый tier

Регламент грамотно запрещает просить паспорт, но разрешает сохранять присланный добровольно, и
складывает в `02_Юридический_блок` паспорта, брачные документы, а позже справки ПНД/НД. Два зазора:

- **Правовое основание.** Скрин переписки (Этап 2.1) фиксирует согласие на работу и комиссию — это
  не согласие на обработку персданных. Справки ПНД/НД — специальная категория ПДн, к ним требования
  жёстче, чем к паспорту.
- **Место хранения.** По `nextcloud-cheatsheet.md` папки сделок отнесены к domain-work tier —
  свободный read+write для агентов; sensitive tier с запретом обхода — это `Офис/БУХГАЛТЕРИЯ`,
  `Офис/БЕЗОПАСНОСТЬ` и т.п. То есть паспорта окажутся в каталоге, который агент обходит свободно.
- Плюс фото из Telegram уходят в `Офис/НЕДВИЖИМОСТЬ/ВХОДЯЩИЕ/`
  ([`photo_disposition_callback.rb:28`](../../../app/services/telegram/work_bot/callbacks/photo_disposition_callback.rb:28))
  — мимо `02_Юридический_блок` и мимо любого tier-контроля. Ровно тот случай из правила 2, когда
  клиент прислал паспорт сам.

### S6. П.13 SLA не наблюдаем: в TopNLab API нет задач

В [`Topnlab::Client`](../../../app/services/topnlab/client.rb) есть `get_notes` / `set_note`,
`patch_entity`, `import_client`, `transfer_client` — **ни одного task-эндпоинта**. «Отметить задачу
"Сбор документов" как ИСПОЛНЕНО» существует только в UI CRM, наша система этого события не видит.
Следствие: п.13 и п.14 не измеряются, а Шаг 2 («в течение 1–2 дней после Шага 1») по-прежнему не
имеет машинного события старта — см. ревью Шага 2, finding **R3**.

Хорошая новость по соседней строке: **п.12 автоматизируем уже сейчас** — `set_note` умеет писать
примечание, `Nextcloud::ShareLinkGenerator` умеет share-link, `DealFolderResolver` знает путь.
Связка «создать папку → получить ссылку → положить в примечания» собирается из готовых кусков.

### S7. Нет ветки «база недоступна»

П.6 и п.10 дают жёсткие тайминги (20 и 30 минут) на проверки в МВД, ФНП, ФССП, ЕФРСБ. Эти сервисы
периодически лежат и капчатся. Красная кнопка (Этап 3) описывает поведение клиента, а не отказ
внешнего сервиса — что делать стажёру, когда база не отвечает, регламент не говорит, и таймер при
этом идёт. Отдельно: скриншот «успешной проверки» без видимых даты и времени в кадре ничего не
доказывает через полгода.
