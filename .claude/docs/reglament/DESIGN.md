## 1. Что мы имеем и в чём задача

Пять регламентов описывают полный путь объекта: от первого документа до принятого задатка. Суммарно
**55 строк SLA** с конкретными дедлайнами — от «0 минут» до «раз в месяц». Документы написаны
практиком: ловушки в них не абстрактные, а те, на которых агентство обожглось.

Машинно измеримых строк из 55 — **ноль**.

Это не дефект текстов. Регламенты писались как инструкция человеку, и как инструкция они работают.
Задача дизайна — не переписать их, а дать им исполняющую среду: чтобы «завершено» было событием, а
не фразой в чате, и чтобы дедлайн кто-то считал.

### Границы

| В периметре | Вне периметра |
|---|---|
| Состояние объекта в конвейере Шагов 1–5 | Собственный CRM: `Property` остаётся проекцией Topnlab |
| Задачи, дедлайны, эскалации по шагам | Замена Telegram на веб-интерфейс |
| Структура папок сделки в Nextcloud | Шаг 6+ (подготовка и проведение сделки) — регламент не передан |
| Отчётность по SLA из данных | Автоматическая подача объявлений на площадки |

## 2. Диагноз: четыре системных дефекта, а не 40 частных

Сорок с лишним находок из пяти ревью сводятся к четырём причинам. Чинить надо их.

### Д1. Нет сущности «объект в работе»

`LeadEvent` моделирует воронку **покупателя** (`new → first_contact → show → contract → deal`) — это
Шаги 4–5. Для Шагов 1–3, где работа идёт с **продавцом и объектом**, в системе нет ни модели, ни
состояний, ни событий. Объект существует как `Property` (проекция каталога) и как папка в облаке —
но «на каком шаге он сейчас» не знает никто, кроме памяти агента.

### Д2. Завершение шага — свободный текст

Все пять регламентов заканчиваются одинаково: «написать в рабочий чат *«Шаг N по [Адрес] —
завершён…»*». Пять разных фраз, ни одна не парсится. Отсюда: дедлайн следующего шага не с чего
отсчитывать (Шаг 2 «в течение 1–2 дней после Шага 1»), просрочка не детектируется, отчёт по портфелю
собирается перечитыванием переписки.

При этом в work-bot уже есть все нужные примитивы: `Task` с `due_at` и `acked_method`, команды
`/close` и `/stage`, `hashtag_handler`, inline-кнопки, `Sla::PingService` с дедупом и quiet hours.

### Д3. Работа ведётся в системе без исходящих событий

Регламенты трижды опираются на задачи в TopNLab: «Сбор документов» → Исполнено (Шаг 1, п.13),
«Показ» (Шаг 4, п.7), статус «Аванс/Задаток» (Шаг 5, п.7). В
[`Topnlab::Client`](../../../app/services/topnlab/client.rb) **нет ни одного task-эндпоинта** —
есть `get_notes`/`set_note`, `patch_entity`, `import_client`, `transfer_client`. Задачи живут только
в UI CRM, наружу не отдаются, нашей системе невидимы.

Асимметрия: у нас есть [`Task`](../../../app/models/task.rb) с `kind: call/show/document/admin`,
статусами, `due_at`, скоупами `overdue`/`due_today` и тремя способами подтверждения. Регламент
выбрал ту систему, которая не умеет говорить.

### Д4. Три конкурирующие схемы путей в Nextcloud

| Источник | Схема |
|---|---|
| Регламенты 1–3 | `[CRM]_ПРОДАЖА_[Объект]` + подпапки `01_Документы` / `02_Юридический` / `03_Фото_Видео/{Исходники,Готовые_для_рекламы}` |
| [`DealFolderResolver`](../../../app/services/nextcloud/deal_folder_resolver.rb) | `<ID> ПРОДАЖА <дескриптор> <Имя клиента>`, подпапок не создаёт |
| work-bot фото | `Офис/НЕДВИЖИМОСТЬ/ВХОДЯЩИЕ/<дата>/` и `.../ПО ЛИДАМ/<id>/` |

Три места для файлов одного объекта. Ни одно не является надмножеством других.

## 3. Высокоуровневый дизайн

Принцип: **регламент — это данные, а не текст**. Шаги, их задачи и дедлайны описываются в YAML
(как уже сделано для топиков в `config/telegram_topics.yml`), а исполнение опирается на модели,
которые в проекте уже есть.

```
                          config/reglament_steps.yml
                       (шаги, задачи, дедлайны, роли)
                                     │
                                     ▼
   Topnlab ──sync──►  Property ──►  ListingPipeline  ──generates──►  Task[]
   (источник                        current_step 1..5                 kind/due_at/
    правды по                       step_entered_at                   assignee
    объекту)                        step_deadline_at                       │
                                         │                                 │
                          ┌──────────────┼──────────────┐                  │
                          ▼              ▼              ▼                  ▼
                   NC-структура    StepCompleted    LeadEvent        Sla::PingJob
                   01_/02_/03_        event         (Шаги 4–5)      (дедуп 30 мин,
                   ensure_structure!    │            stages          quiet hours)
                          │             │                │                 │
                          └─────────────┴────────────────┴─────────────────┘
                                              │
                                              ▼
                                    Telegram work-bot
                              #ДИСПЕТЧЕРСКАЯ · #ОТЧЕТЫ ПО SLA
                              кнопка [✅ Шаг N завершён]
```

**Поток одного объекта.** Агент берёт объект в работу → `ListingPipeline` создаётся на шаге 1 →
из YAML разворачивается набор `Task` с дедлайнами от `step_entered_at` → бот кладёт их в
#ДИСПЕТЧЕРСКУЮ и в DM исполнителю → агент закрывает задачи кнопкой → когда закрыты обязательные
задачи шага, бот предлагает `[✅ Шаг 1 завершён]` → нажатие пишет `StepCompleted`, двигает
`current_step`, разворачивает задачи следующего шага и ставит отсчёт его дедлайнов. Просрочка любой
задачи → существующий `Sla::PingJob`.

Свободнотекстовый рапорт при этом никуда не девается — он остаётся человеческим сопровождением
события, но перестаёт быть его носителем.

## 4. Детальный разбор

### 4.1 Модель данных

Одна новая таблица. Всё остальное — переиспользование.

```ruby
# db/migrate/..._create_listing_pipelines.rb
create_table :listing_pipelines do |t|
  t.references :property,   null: false, foreign_key: true
  t.references :agent,      foreign_key: { to_table: :telegram_users }
  t.string   :current_step, null: false, default: 'step_1'   # step_1..step_5, completed, aborted
  t.datetime :step_entered_at, null: false
  t.datetime :step_deadline_at                                # вычисляется из YAML
  t.jsonb    :step_history, null: false, default: []          # [{step:, entered_at:, completed_at:, by:}]
  t.jsonb    :metadata,     null: false, default: {}          # nc_folder_path, youtube_url, tax_check, …
  t.datetime :deleted_at                                      # soft delete, правило 1 CLAUDE.md
  t.timestamps
end
add_index :listing_pipelines, :current_step
add_index :listing_pipelines, :deleted_at
```

Конвенции проекта соблюдены: `enum :current_step, {...}, prefix: true`, `deleted_at` +
`default_scope { not_deleted }`, никакого `paranoia`.

**Почему `metadata` как jsonb, а не колонки.** Шаги требуют хранить разнородные единичные факты:
ссылку на YouTube (M3), вывод по ст. 217.1 (D4), статус одобрения объекта банком (D5), путь к папке
NC. Каждый — по одному значению на объект, все появляются в разное время. Отдельные колонки под них
дадут таблицу-простыню с nullable-полями; вынос в связанные таблицы — оверинжиниринг для одного
значения. Ровно тот же приём уже применён в `LeadEvent#metadata` (там же живёт `last_sla_ping_at`).
Цена решения: нет типизации и внешних ключей — компенсируется валидацией по схеме на входе.

### 4.2 Регламент как данные

```yaml
# config/reglament_steps.yml — правится без деплоя, как telegram_topics.yml
step_2:
  title: "Предпродажная подготовка и фотосъёмка"
  doc: ".claude/docs/reglament/step-02-staging-photo.md"
  entry_deadline: 2.days          # «в течение 1–2 дней после Шага 1»
  tasks:
    - key: audit_visit
      kind: admin
      title: "Выезд на объект, аудит состояния"
      due_in: 2.days
      role: agent
      required: true
    - key: upload_originals
      kind: document
      title: "Загрузить исходники в 03_Фото_Видео/Исходники"
      due_in: 1.day
      after: photo_session         # отсчёт от завершения другой задачи, не от начала шага
      required: true
      completion: nc_file_present  # авто-проверка вместо кнопки
```

Три типа завершения задачи, по убыванию надёжности:

| `completion` | Как закрывается | Где применимо |
|---|---|---|
| `nc_file_present` | проверка `Nextcloud::Client#exists?` | загрузка файлов (Шаг 1 п.4, Шаг 5 п.5) |
| `crm_field` | значение поля в `Property` после синка | статус «Аванс/Задаток» (Шаг 5 п.7) |
| `manual` | кнопка `[✅ Выполнено]` / `/done` / реакция ✅ | всё остальное |

`manual` — не поражение: `Task#acked_method` уже различает три способа подтверждения, а
`suspicious_flag` в [`task.rb:155`](../../../app/models/task.rb:155) уже ловит подозрительные
закрытия (call-задача закрыта, а `first_contact_at` пуст). Тот же приём распространяется на шаги.

### 4.3 Единый примитив завершения шага

Замена пяти разных фраз одним событием:

```
[✅ Шаг 2 завершён]  ← inline-кнопка, появляется когда закрыты required-задачи шага
        │
        ├─ ListingPipeline#complete_step!(by: tg_user)
        │     ├─ step_history << {step:, entered_at:, completed_at:, by:}
        │     ├─ current_step = next
        │     ├─ step_entered_at = now; step_deadline_at = now + entry_deadline
        │     └─ TaskGenerator.for(pipeline)  → задачи следующего шага
        │
        └─ бот постит в #ДИСПЕТЧЕРСКУЮ человекочитаемый рапорт —
           тот самый текст из регламента, но теперь как следствие события, а не вместо него
```

Команда-дублёр для тех, кому привычнее текст: `/step done <адрес>`. Расширение
`callbacks/task_action_callback.rb` и `commands/close.rb` — оба уже есть.

### 4.4 SLA-движок: ничего нового

`Sla::PingService` сегодня умеет один вид пинга — `:first_contact_overdue` по `LeadEvent`. Нужно
добавить `:task_overdue` и `:step_overdue`, переиспользовав всё остальное как есть:

- дедуп через `metadata['last_sla_ping_at']`, окно 30 минут — уже реализован;
- quiet hours 21:00–07:00 MSK с `perform_at` — уже в `PingJob`;
- guard на неактивного исполнителя с эскалацией менеджеру — уже в `ping_service.rb:32`;
- cron — строка в `config/sidekiq_cron.yml` (не в `schedule.rb`, см. CLAUDE.md).

Единственное содержательное решение — **эскалационная лестница**, которой в регламентах нет:

| Просрочка | Действие |
|---|---|
| дедлайн задачи | DM исполнителю |
| +2 часа (или +1 день для суточных) | пинг в #ДИСПЕТЧЕРСКУЮ с упоминанием |
| дедлайн шага | эскалация руководителю с карточкой объекта |
| «0 минут» (Шаг 1 п.11, блокеры) | немедленно в #ДИСПЕТЧЕРСКУЮ, quiet hours **игнорируются** |

Последняя строка — намеренное исключение из quiet hours: `quiet_hours.rb:10` уже содержит
прецедент («лид от клиента в 22:00 должен попасть в #ДИСПЕТЧЕРСКОЙ сразу»).

### 4.5 Nextcloud: одна структура вместо трёх

```ruby
# Nextcloud::DealFolderResolver — добавить
SUBFOLDERS = ['01_Документы_по_объекту',
              '02_Юридический_блок',
              '03_Фото_Видео/Исходники',
              '03_Фото_Видео/Готовые_для_рекламы'].freeze

def self.ensure_structure!(property:, inquiry: nil, client: Nextcloud::Client.new)
  # идемпотентно: mkcol на каждый уровень, существующие пропускаются
end
```

Следствия:
- Шаг 1 п.3 («создать папки, макс. 15 мин») из ручной операции становится авто-действием при входе
  объекта в конвейер. Одна из немногих строк SLA, которая исчезает целиком.
- `03_Фото_Видео` перестаёт быть фантомным путём (R1/S2/M4 закрываются разом).
- `photo_disposition_callback` получает четвёртую цель диспозиции — «в папку объекта», рядом с
  существующими general/lead; `ВХОДЯЩИЕ/` остаётся тем, чем задумывался, — транзитным приёмником.

**Открытое решение за агентством:** имя папки. Схема кода (`<ID> ПРОДАЖА <дескриптор> <Имя>`) уже в
проде и резолвится из `Property` автоматически; схема регламента (`<ID>_ПРОДАЖА_<Объект>`) — нет.
Рекомендация — привести регламенты к коду, а не наоборот; но это вопрос удобства людей, которые
ищут папку глазами, и решать его им.

### 4.6 Контракты с внешними системами

| Система | Направление | Что меняется |

## 5. Чего дизайн намеренно не делает

- **Не заменяет TopNLab.** Задачи ведутся у нас, потому что у CRM нет task-API; карточка объекта,
  цена, статус сделки остаются в CRM. Двойного ведения одних и тех же данных быть не должно.
- **Не строит веб-интерфейс.** Сотрудники живут в Telegram, бот — фактический CRM-канал. Ещё один
  UI означает третье место, куда забывают вносить.
- **Не автоматизирует содержание работы.** Никакой ИИ не проверит паспорт по базе МВД и не проведёт
  показ. Автоматизируется учёт, а не работа.
- **Не трогает Шаг 6+.** Регламент подготовки к сделке не передан; проектировать под догадку нельзя.

## 6. Нагрузка и надёжность

**Нагрузка не является проблемой, и притворяться иначе не нужно.** Порядок величин: десятки—сотни
активных объектов, ~11 задач на объект по всем пяти шагам, то есть тысячи строк `Task` в год. Для
PostgreSQL это ничто; cron уже гоняет 22 задачи в Sidekiq. Единственный реальный расход — сообщения
в Telegram, и он ограничен не мощностью, а терпением сотрудников: слишком частые пинги обучают людей
игнорировать бота. Поэтому дедуп и quiet hours важнее производительности.

Что действительно требует внимания:

| Риск | Смягчение |
|---|---|
| Агент закрывает задачи, не делая работу | `suspicious_flag` (уже есть) + авто-проверки `nc_file_present` там, где возможно |
| Объект «застрял» на шаге месяцами | `step_deadline_at` + недельный дайджест зависших в #ОТЧЕТЫ ПО SLA |
| Nextcloud недоступен при `ensure_structure!` | идемпотентность + повтор в Sidekiq; шаг не блокируется |
| Двойной клик по кнопке завершения | `complete_step!` идемпотентен по `current_step` |
| YAML сломан правкой без деплоя | спека, валидирующая схему всех шагов (прецедент: `telegram_topics.yml`) |

## 7. Компромиссы

| Решение | Плюс | Цена | Почему так |
|---|---|---|---|
| Регламент в YAML, а не в коде | правится без деплоя, руководитель видит структуру | нет типизации, ошибка проявится в рантайме | прецедент `telegram_topics.yml` живёт с мая, схема закрывается спекой |
| Задачи у нас, а не в CRM | события, дедлайны, отчёты | стажёр видит две системы | у CRM нет task-API — альтернативы нет |
| `metadata` jsonb | гибкость под разнородные единичные факты | нет FK и типов | по одному значению на объект; прецедент `LeadEvent#metadata` |
| Telegram как единственный UI | сотрудники уже там, ноль обучения | нет табличного обзора портфеля | обзор закрывается дайджестом и `director_dashboard` |
| Кнопка вместо авто-детекта | работает для любого шага | доверие к нажатию | `suspicious_flag` + авто-проверки там, где файл/поле проверяемы |
| Одна модель на пять шагов | простая, один жизненный цикл | Шаги 4–5 частично дублируют `LeadEvent` | `ListingPipeline` про объект, `LeadEvent` про покупателя; на объект приходится много лидов |

## 8. План по фазам

Порядок выбран по отношению «эффект / риск», а не по номерам шагов.

### Фаза 0 — решения без кода (нужны от агентства)

Четыре вопроса, каждый блокирует код ниже:

1. **Имя и структура папки сделки** — схема кода или схема регламента (§4.5).
2. **Авито: фид или руки** — подключён ли `feeds/avito.xml` в кабинете. От ответа зависит судьба
   правила «только черновик» и ежемесячного перевыпуска ([M1, M2](step-03-marketing-launch-review.md)).
3. **15 или 30 минут** на первый ответ — двигать регламент или метрику
   ([I1](step-04-inbound-shows-review.md)).
4. **Названия топиков** — `ЗАДАТОК` или `⁉️ ЗАДАТОК`; переименование в TG ломает реестр молча
   ([D3](step-05-deposit-fixation-review.md)).

### Фаза 1 — деньги прямо сейчас (~1 PR, полдня)

`prepayment` в `EXCLUDED_FROM_CATALOG` + спека на `in_advertising`. Объекты с задатком перестают
уходить в XML-фиды; рекламный бюджет и звонки по проданному прекращаются
([D1](step-05-deposit-fixation-review.md)). Единственная находка всего ревью, которая исправляется
одной строкой и даёт эффект в тот же день. Отдельный PR — меняет поведение трёх публичных фидов.

### Фаза 2 — структура облака (~2–3 PR)

`SUBFOLDERS` + `ensure_structure!` + диспозиция фото в папку объекта + `set_note` со ссылкой на
корень. Закрывает R1/S2/M4/D6 и снимает две строки SLA (Шаг 1 п.3, п.12) из ручного режима.
Предусловие — решение 1 из фазы 0.

### Фаза 3 — конвейер (~5–8 PR стеком)

`ListingPipeline` → `config/reglament_steps.yml` → `TaskGenerator` → кнопка завершения шага →
`/step` команда. Едет стеком PR по правилам `gh-stack`: миграция → модель → генератор → бот-слой.
Здесь появляется само событие «шаг завершён» и осмысленные дедлайны.

### Фаза 4 — отчётность (~2–3 PR)

`:task_overdue` / `:step_overdue` в `Sla::PingService`, эскалационная лестница, недельный дайджест
портфеля в #ОТЧЕТЫ ПО SLA, дашборд «объекты по шагам» в `director_dashboard`. Появляется ответ на
вопрос «где стоит портфель», которого сегодня нет ни у кого.

Фазы 1 и 2 самостоятельны и дают пользу без фазы 3. Если конвейер не будет построен, они не
пропадут зря — это осознанная развязка.

## 9. Что пересмотреть при росте

| Триггер | Что менять |
|---|---|
| >500 активных объектов | `step_history` в jsonb перестанет быть удобным для аналитики → отдельная таблица `step_transitions` |
| Больше 2–3 агентов на объект | роли в `ListingPipeline` (сейчас один `agent_id`) → таблица участников |
| Появление Шагов 6+ | проверить, что `current_step` как enum не станет простынёй; возможно, отдельный конвейер на пост-задаточную фазу |
| У TopNLab появится task-API | пересмотреть Д3: возможно, задачи вернутся в CRM, а у нас останется только SLA-надстройка |
| Регламенты начнут меняться чаще раза в квартал | версионирование YAML: объект должен доигрывать по той версии регламента, на которой начал |

## 10. Открытые вопросы

- **Кто владелец регламентов в системе?** Сейчас правки приходят текстом от руководителя. Нужен
  договорённый маршрут: источник → импорт → ревью → PR.
- **Что считать началом конвейера?** Шаг 1 стартует «после сообщения руководителя в группе» — это
  событие в WhatsApp/Telegram, которое системе не видно.
- **Роль стажёра.** В Шагах 1 и 5 исполнитель — «стажёр», в 2–4 — «агент». Если это одна роль,
  надо унифицировать; если разные — описать, что происходит с объектом без стажёра
  ([D8](step-05-deposit-fixation-review.md)).
- **Шаг 6.** Без него цепочка обрывается на принятом задатке, а самая рискованная часть сделки
  остаётся вне регламентов.
